# 中心库字形账本恢复（被空账本清空／误删之后）

> 原 cv `doc/runbook/恢复中心库字形账本.md`（2026-11-04 殿本 siku-zongmu 被空壳 sync 清空后的恢复，import 1199），11-22 移来。
> 当时中心库在 Neon，靠「时间点分支」留底；**11-18 起中心库已在 Cloudflare D1，Neon 已删**，留底改用每日备份（`guji datastore backup`，R2 正式桶 `backup/<日期>/`）或 D1 自带的时间点恢复。D1 下的具体留底步骤还没演练过，用之前先按 [doc/参考/中心库](https://github.com/open-guji/guji-manager/blob/dev/doc/参考/中心库.md)「备份与恢复」核一遍。

## 先止血（几分钟）

1. 找到并停掉还在推的循环（定时 sync、各会话的 auto_cycle／proof_cycle）。看 `imports` 里最近的 push：`actor`、`source`（`push:<ws>@<base>`）、`stats.problems`。actor 为空的，多半是没设 `GUJI_ACTOR` 的云会话。
2. **立刻留底**：确定救援点（出事 import 的 `started_at` 前一刻），找到最近的完整每日备份，或用 D1 时间点恢复到新库；核对 `max(changes.rev)`、各 `glyph_*` 表按 `ws` 的行数。
3. 通知各方暂停对该工作区 push／sync。

## 恢复（写中心库，要用户点头）

1. 沙箱里 `GUJI_DATA_HOME=<临时目录>`，建 `workspace.yaml`（`id: <ws>`）和 `.central.json`（`{"ws":"<ws>","branch":"main"}`）。
2. `guji db pull -w <沙箱> --no-rebuild` 拉**当前** main（含出事后别人的合法写入）。
3. 另起一个目录，从救援点取出该工作区的字形账本（`output/glyph_store/` 的账本 jsonl 和 `patches/`）。
4. 把救援点的账本覆盖到第 2 步的目录。
5. `guji db push -w <沙箱> --dry-run`：逐表对照出事 import 的 `stats.per_table`（应是它的镜像：insert 对应当时 delete），`problems` 为空，`files／events／books` 无变更。
6. 真推，设 `GUJI_ACTOR`。图已在 R2 时上传核对很慢，可直接写库（图按 sha 在桶里）。
7. 核对：各表行数与救援点一致；按主键排序逐表比哈希。
8. 通知各方 `guji db pull --force` 本机副本（先备份），确认账本非空再开循环。

## 预防（已在代码里）

- 推库必须有操作人（`GUJI_ACTOR`）。
- 本地字形账本不到库里一半且要删一半以上时拒推（`--allow-delete` 放行）。
- 删本机 `glyph.db` 之前先 `guji db pull --force`，别用 sync 去「修」glyph.db。
