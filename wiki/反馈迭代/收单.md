## 一、收单是哪一段

读者在网站投票（意见，按条目存进 `web_inbox`，键 `cr:i:<书>:<条目>:<投票人>`）→ **落票**成裁定事件（`channel=web_vote`）→ 定字直接写 **book-text** → 条目标 `resolved` → **推库** → 网站下一次读就不再显示这格。

两条硬规矩（用户定，不随本文改）：
- book-text 只录首选字；待审原因、候选、裁定事件都在中心库。
- 机器结果不覆盖已落定的裁定；裁定一票即算，不做多人投票或双路复核（落票策略 `--policy` 见下）。

## 二、一条命令收单

```
guji feedback collect --books auto -w <工作区> --book-text <book-text 检出> [--reviewer <名>] [--dry-run]
guji feedback collect --books vol20,vol21 …        # 指定册
```

**各书第一次用先 `--dry-run`**，看 `draft/` 下的草稿和 `落文本.json` 再真跑。执行机约每 30 分钟自动跑一次（没新票的册 `auto` 自动跳过），清单推 ai-team「交项目确认」。

| 步 | 做什么 |
|---|---|
| 0 | `--books auto`：读收件箱的票，挑出有票落在还开着的条目上的册 |
| 1 | `db pull` 一次（增量） |
| 2 | `cellvotes draft --items` → `cellvotes write`：票按 `(书, 册, u)` 对到现在的格，写成裁定事件（`level=human`，`by`＝`member:<会员号>`／`anon:<16 位>`，`channel=web_vote`）；落了票的条目标 `resolved` |
| 3 | 定字票（本次新写的，加上「与已有裁定一致」跳过的）逐格对 book-text dev 现文：字不同就写裁定的字（去 lacuna），标点 `pre_char`、专名 `text` 跟改，升 patch、`local_check --dev`、推 dev（1.x 册推 `swap/<册>-1x` 开草稿 PR）；格框对不上、以图代字格不写，报出来等下一轮 |
| 4 | `--batch <早先裁定批次>`（可重复）：库里早先写下、还没进 book-text 的裁定一起落（过绑定表、每格取最新）；只有 `u` 锚的批次按 `u` 在 book-text 查格 |
| 5 | `db sync` 一次 → 核线上：本次定了字的格不再待审 |

AI 裁定（文意、终审看图）在没有人级裁定的格上也一起落，条目不结案（用户 11-20 定，`--no-ai` 关）。

**落票策略** `--policy`：`auto`（缺省）、`quorum:N`、`rules`（按投票人是会员／等级／负责的书决定票能否直接落，见 `feedback/landing_policy.py`）。挂起（意见不一致、推翻旧裁、格位变了、条目图变了）、切分类、无字票不落，留在 `held`／`waiting` 里，看 `draft/report.md`。

- **断点续跑**：状态在 `<工作区>/reports/<册>/_collect/…/state.json`，每步记一笔；停了原命令再跑，做过的跳过；`--fresh` 从头。收完一趟后同一批条目又来了新票，再跑就是新的一趟。
- **多册并行**：`--jobs 4`（4–8 路）。拉库、取 book-text dev、推库各在父进程做一次；每册一个子进程，各用 `<检出>-collect-<册>` worktree，推 dev 被抢先就 rebase 重推。各册日志在 `<工作区>/reports/_collect/runs/<本趟>/<册>.log`。
- **取包**：包分段并发取；每册收完自动删 `_packs/<标签>/<册>`（`--keep-pack` 留着）。
- **`--dry-run`**：只拉库、读票、算要落哪些格，book-text 改动提交在 worktree 不推；不写裁定、不推库、不留进度。
- **落哪个字、落哪一格**：票、裁定都带 `u`，按 `(书, 册, u)` 跟到现格（u 已作废的票挂起为 `moved`，进复审）；一律取 cv `human_chars`（过绑定表，只认 `valid`／`rebound`）；算不出来就停、不落 book-text。
- **提示词改版的文意裁定**：裁定按窗口键没命中，但这格最新一条裁定的窗口与现在的 ask 相同、只是提示词版本或字组名变了，照样落（来源记 `AI文意/<组>/改版重键`），并补写一条按现行组／版本的裁定（批次 `llm-rekey-collect-<册>-<时刻>`）；窗口变了的仍不认（用 `guji text rulings-hits --rekey`）。
- **网络读超时**（R2／中心库 SSL timeout、StaleBase）：拉库、读票、落票、推库在这一步里重试，不整册重来。
- **机器产物要等下一轮重放才跟上裁定**，期间产物字≠book-text 是正常的：裁定最高，重放时 `seed_admit` 认裁定，自然对上。

> **命令行里的 `rev`**：`collect`／`cellvotes` 还有 `--rev`、`--pack rev-<rev>`、`_collect/<rev>/` 这些参数名和路径，是它们读 land 导出的整张 `<章>.pending.json` 的过渡残留，**不是版本概念**，票也不再按 rev 存。land 停导整张单、命令清掉这些参数后，这里同步删。

## 三、什么时候走别的路

| 情形 | 走法 |
|---|---|
| 标了新 main，要让条目跟上新包 | `guji pipeline … ` 出包即收尾（`guji land`），见 [待审条目上线](待审条目上线)；批量 `guji feedback swap run --books <段>`（名可写 `001-015`） |
| 只落票、不改文本 | `guji feedback cellvotes draft --items` → `write` → `guji db sync` |
| 库里已有裁定、条目还开着 | `guji pending-settle -w <工作区> [--pull] [--apply] [--sync]`：格已落定的开着条目标 `resolved`，复审格要裁定晚于复审开出才关；执行方 `GUJI_PENDING_SETTLE_S` 定时跑 |

增量拉退回整拉的情形：整批导入、变更超过 2 万条或文件超过 400 个、`pull --force／--exclude／--repair-gaps`、新机器。`GUJI_DB_FULL_PULL=1` 强制整拉，`GUJI_DB_FULL_SCAN=1` 强制整扫推。

## 四、收单前后要核的

1. **先问用户有没有正在投的册**；`swap run` 遇到正在投的册会判 waiting、不换，这是对的。
2. **票的闸**（「还有 N 格的票没落成裁定」）：确认票都已落成裁定才用 `--ack-unlanded-votes "<原因>"`。全唐文 QTW 报 Sheldon 11-17 定这三类（切坏票、看不清票、已有同样裁定）以后一律放行；别的书、别的类型仍要用户点头。
3. **重切过的册**先按新包重建字块缓存，再落票。
4. **收完核线上**：`curl https://www.openguji.com/api/pending?book=<书ID>&vol=<章>`，本次结案的格不应再出现；proofing-sync 显示 success 不算数。
