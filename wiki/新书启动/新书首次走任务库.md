# 新书首次走任务库：顺序与坑

> 属于 [第一步 新书启动](第一步-新书启动)。原 cv `doc/runbook/新书开工与首次走任务库.md`（2026-10-31 史記文淵閣本第一次在任务库上跑时踩的坑），11-22 cv 文档重整时移来。

新书第一次把整册交给任务库（`guji pipeline job`）在执行机上跑之前，照下面顺序做，前一步没过不做下一步。

## 一、顺序

1. **建工作区仓**：`guji-workspace` 组织下一书一仓，仓根即工作区（`workspace.yaml`、`.central.json`），工作区 id ＝ Book ID。
2. **登记到任务库**：`guji_manager/jobs/spec.py` 的 `WS_REPOS` 加「书 ID → 仓」，PR 投 manager dev。
   不登记就要在每张单里手写 `ws_repo`；漏写时执行方去旧总仓找目录，报 `ls: cannot access '/root/guji-workspace/<书ID>-*'`。
3. **册配置齐了再推**：各册 yaml 的开关、语料、钉页表推中心库（`guji db push`）。
   - 配了 `row_segment.layout_prior`（离线格位表）的册，表里要有这一册，否则 Step3 整册报错（`layout_prior 表 … 里没有 NN`）；用钉页表的书改用 `page_map: pins`。
   - **推之前查字形库真源**：`ls <数据目录>/output/glyph_store/instances/`，人裁过的书这里应有本书实例；为空见第三节第 1 条。
4. **字形库出快照并钉号**：`guji pipeline glyph-db snapshot -w <工作区>` 出 `g<N>`，各册 yaml 写 `glyph_pin: N`，推中心库。执行方按快照拼出和本机逐字节相同的库；不钉号时执行方用自己重建的库，不一定一样。
5. **交单**：`GUJI_JOBS_WHO=<名字> guji pipeline job submit spec.json`。spec 写 `ws_glob: "<书ID>-*"`（不写会落到缺省的殿本）和 `cv`（远端能取到的分支／tag／提交）。从没存过产物包的书只能跑全流程，不能 `--from` 中途起跑。先 `--dry-run` 看规整后的书 ID 和 `ws_repo`；交单前跑 `guji pipeline job precheck`。
6. **验结果**：`guji pipeline products pack fetch <册> --label <包标签> --root <目录>` 拉回来，和本机同配置的结果比待审数；比 glyph_match 的 same 数最快能看出字形库对不对。对不上就别用这批包。

## 二、症状 → 原因

| 症状（`guji pipeline job show`） | 原因 | 处理 |
|---|---|---|
| prep「更新工作区」`ls: cannot access '/root/guji-workspace/<书ID>-*'` | 单子里 `ws_repo` 为空：书没登记 `WS_REPOS`，或交单机器上的 manager 早于登记 | 登记；单子里写明 `ws_repo` |
| 单子成功，但待审率比本机高几倍、glyph_match 几乎没有 same | 执行方字形库缺本书字样（第三节第 1 条） | 修真源、出快照钉号后重跑 |
| Step3 整册失败 `layout_prior 表 … 里没有 NN` | 离线格位表没这一册 | 补表，或改 `page_map: pins` |

## 三、坑的来龙去脉

1. **借库冷启动的书，人裁实例没进字形库真源**（cv #816 已修）：旧的导出遇到借来库的 source 整个跳过，本书人裁全丢，中心库 `glyph_store/instances/` 为空；本机 glyph.db 里有，所以只有换机器才露馅。修后重新 `guji pipeline glyph-db export` 再推。
2. **`ws_repo` 在交单那一刻按交单机器上的 `WS_REPOS` 填**：本机检出是旧版本时，即使 dev 已登记也填不上。
3. **本机跑和任务库跑别混**：同一册本机在跑时交单，结果会打架。交单前停掉本机重跑，或只交本机没跑的册。
4. **长跑别放 Bash 后台**：后台缺省 30 分钟超时会被杀；一册全流程 15–25 分钟，十册串跑交任务库。
