# 重跑需求与执行规范（A30 接单用）

> 2026-10-23 起草（A30，sheldon 定方向）；**2026-10-25 起改为交任务库**（用户定：传话不准、各会话互不知道别人在跑什么）。依据：open-guji-cv `doc/design/重跑任务库.md`、`doc/受控重跑.md`、`doc/exp_framework.md`，以及本目录的[受控重跑方法论](受控重跑方法论.md)、[冻结基线与重跑分级](../03-精校/冻结基线与重跑分级.md)。命令细节以 cv 仓文档为准。
> 时间一律洛杉矶时间。

## 一、一句话
要重跑、A/B、评测，**自己往任务库交一条任务**（Neon 中心库 `jobs` schema，命令 `guji_jobs submit`），不再给 A30 发需求单、不经协调者传话。定时任务每小时看一次库，有排队的单就开执行会话一口气跑完：准备→铺底→人裁检查→跑→对比→存包（不标 main）。谁交了什么、谁在跑、跑到哪一步、包存在哪，所有会话 `guji_jobs ls／show` 都看得到，跑完不用谁通知谁。同一配置（指纹相同）只跑一次，重复提交直接指向已有那条。

```bash
export GUJI_JOBS_WHO=A24          # 你的名字，记进提交人
guji_jobs ls                       # 先看有没有人已经在跑同样的
guji_jobs submit --book vol10 --cv v0.5.16 --from seed_admit --human-chars 146 \
  --compare-to main --change seed-xxx --why "A24：要回答什么问题"
guji_jobs show <号>                # 进展、结果（包标签、R2 位置、对比报告开头）
guji_jobs wait <号>                # 等它结束
```

`guji_jobs` 在 Default 环境里预装（总跑 cv dev 最新的任务库代码，和你装的 cv 版本无关）；没有就 `git -C /opt/guji-cv-seed fetch -q origin dev && git -C /opt/guji-cv-seed show origin/dev:scripts/guji_jobs.sh > ~/guji_jobs && bash ~/guji_jobs …`。

## 二、管线步骤与起点（`--from` / `--to` 用的步骤 id）
管线 `keben_body_v2`，顺序固定：

| 步 | id | 说明 |
|---|---|---|
| 0 | `page_survey`、`invert_detect` | 页面预检、反色带候选 |
| 1 | `border_detect`、`seal_detect` | 版框界行、印章 |
| 2 | `column_warp` | 单列射影，挂出口闸 `column_gate` |
| 3 | `row_segment` | 单列文字切分 |
| 4 | `cell_shrink` | 字框收缩 |
| 5-a | `glyph_match` | 库匹配 |
| 5-b | `rare_candidates` | 生僻字候选（要预备模板索引） |
| 5-d | `align_ref` | 整理本对齐 |
| 6 | `context_decide` | 上下文裁决 |
| 7 | `seed_admit` | 进库准入（放行或送审） |

两个常见说法的对应：
- **「只跑 1–4 步，测切分」**：`guji pipeline keben_body_v2 <册> --from <起点> --to cell_shrink`（整册从头就不写 `--from`）。v0.5.7 的 `--to column_gate` 报错，要停在 Step2 用 `--to column_warp`。
- **「从 5b 开始」**：`--from rare_candidates`。注意：**只改形近字组、规则、L2 表、书级用字时，第一个过期的步是 `seed_admit`**（方法论第二节表），不必从 5b 起；5b 只在字体域、生僻字模型、模板索引变了才需要。需求单里写清「改了什么」，A30 先用 `guji status <册> --pages all` 核实第一个过期步，和需求方写的起点不一致就先回问，不自己拍板。

## 三、任务怎么写（旧「重跑需求单」各项对应的字段）

| 旧需求单的项 | 任务字段（命令行参数） | 说明 |
|---|---|---|
| 需求方 / Jira 卡 | `GUJI_JOBS_WHO`、`--why` | why 写清谁要、要回答什么问题、Jira 卡号 |
| 用哪版代码 | `--cv`（**必填**） | tag、分支、提交都行，提交时钉成 40 位提交；dev 也钉成当时的 dev 头 |
| 册与页集 | `--book`、`--pages`（缺省 all） | 一条任务一册；多册交多条 |
| 起点步 → 终点步 | `--from`、`--to`（第二节的 id） | 不写就整条；从中间起跑自动先取 main 包铺底（`--base` 改） |
| 语料号、字形库号 | `--corpus`、`--glyph-pin` | 只改执行会话本机的册配置，不推中心库 |
| 追加语料钉子账 | spec JSON 的 `pin_args` | 同 `guji corpus pin` 的参数 |
| 参数覆盖 | `--params '{"seed_admit":{…}}'`、`--env GUJI_X=1` | env 只收 GUJI_ 开头、不是凭据的 |
| 对比基线 | `--compare-to main｜包标签｜job:<号>` | A/B 用 `--kind ab`，B 的 compare_to 写 A 的任务号，再 `--after <A 的号>` |
| 验收前提 | `--human-chars N` | 开跑前人裁绑定格数必须等于 N，不等就拦下（blocked），不跑 |
| 上传标签名 | `--change`（缺省 job<号>）、`--note` | 永远不标 main；`--no-pack` 不存包 |
| 评测、其他命令 | `--kind eval`／`--run "guji 子命令 …"` | 不经 shell；不许 push／sync／promote／--main |
| 加急 | `--priority 10`（缺省 100，越小越先） | 已排队的用 `guji_jobs bump <号>` |

先 `--dry-run` 看规整后的定义。交错了 `guji_jobs cancel <号>`；失败或拦下的修好原因后 `guji_jobs retry <号>`。
**覆盖正式产物、改册配置推库、标 main、批量删除**任务库都不做，仍等用户明确同意，由人手动做。

## 四、什么可以重跑、怎么改配置

| 要改的 | 在哪改 | 谁改 | 备注 |
|---|---|---|---|
| 册级开关与参数 `params:`、`codepoints`、`layout_prior`、`bottom_gap` | 册 yaml（中心库数据目录 `books/<册>.yaml`，`guji db pull` 后在本机改） | A30 按需求单改 | 合并写入，不整段替换；改完 `guji status` 看哪些步过期。正式册配置推库要用户同意；实验在中心库实验分支（`GUJI_DATA_BRANCH=exp/…`）做 |
| 钉版：`cv_version`、`corpus: N`、`glyph_pin: N` | 册 yaml | A30 | 号加一是有意重跑；`glyph_pin` 第一次写入会让该册 seed_admit 过期一次 |
| 形近字组、规则、L2 表、字组配置 | cv 仓 `config/groups/`、`config/*.json`、代码 | **需求方**走 cv 的 PR（投 dev） | A30 不改 cv 代码和字组数据；只在需求单给的分支或提交上跑 |
| 语料库 | `guji corpus build/pin` | 需求方出新版，A30 只加 `corpus:` 号 | 钉了版本的册，语料被改会拒跑 |
| 临时参数覆盖（不改文件） | `guji pipeline --params '{"seed_admit":{…}}'` 或 `guji exp` 变体 yaml | A30 | 参数名按 Step 的 Params 校验，写错会报错 |

规矩：一次只动一个变量；cv 提交号、语料号、字形库号、册 yaml 的差异都要记下来（第七节）。

## 四·补（2026-10-26）：册配置分层与运行覆盖
设计与实现在 cv `doc/design/册配置分层与运行覆盖.md`（PR #634，随下一个 cv 发版生效）。要点：
- **五层**（低→高）：代码默认 < 管线 yaml < 工作区基础配置 `config/book_defaults.yaml` < 册 yaml < 本次运行覆盖。基础配置放全书共用的（版本钉、group_flow、证人、码位、各步开关），册 yaml 只写册号、图源、实测先验和个别调参。身份与图源（id、title、raw_dir…）、实测先验只能写册 yaml。
- **任务里怎么覆盖**：`book_overrides`（`guji_jobs submit --override '{"corpus":23,"params":{"seed_admit":{…}}}'`）现在可覆盖任意册级字段（身份与图源除外），执行方用 `guji pipeline --override` 在内存里叠，**不改任何 yaml、不推库**，覆盖原文记进产物 manifest `config_overrides`。`--params` 同层，显式传 false 也能关掉册 yaml 开着的开关（旧版会被静默改回，已修）。
- **看生效值**：`guji book show <册> -w … --effective`，每个字段标来自哪一层。
- **什么时候进中心库**：正式决定（新册立档、全书升版本／换语料／开关转正）改基础配置或册 yaml 并 `guji db push`；做实验只用运行覆盖；实验要写库才开 `exp/GUJI-…` 分支。册 yaml 与基础配置永远不进 git。
- **迁移**：`guji book split --books vol51-vol99 [--apply]` 抽共用部分（逐册强校验合并结果与拆前相等）。**含本功能的 cv 版本发出前不迁**：旧版本读瘦身册会静默丢基础配置。

## 五、标准执行流程（任务库执行方自动按这个走；以下是手动执行时的细节）

0. **准备**（云端 Default 环境，4 核 15GB；用户 10-23 定：子会话启动要快，**默认不 clone 任何仓**，用环境预装的 `/opt/guji-venv/bin/guji`，按需求单 pip 装指定 release 版本；只有需求单要求跑 cv dev 分支或未发布提交时才浅克隆 cv，下面的 `scripts/` 命令也只在有 cv 检出时用）：`bash scripts/bootstrap_cloud.sh`；`guji db pull`（约 8 分钟，放后台）；`guji products pack fetch-index`；取「前」`guji products pack fetch <册> --to $SCRATCH/base`；seed_admit 前 `guji cache warm --jobs 4`；起点到 5-b 要先 `guji cache pull-rare-index`。装 `.[console,torch,dev,datastore,shadow,pdf]`，缺 `shadow` 会让 seed_admit 全失败。
1. **沙箱**：`export GUJI_PRODUCTS_DIR=$SCRATCH/new`，把 base 拷一份，`guji pipeline keben_body_v2 <册> --pages <页集> --from <起点> --to <终点> -w $WS`。长任务用 `scripts/longrun.sh start/resume`（容器空闲会回收，进程全死，磁盘保留）。同一时刻只跑一个真书批。
2. **对比**：`guji products diff <册> --a $SCRATCH/base --b $SCRATCH/new --images 40 --out diff-<册>`。验收顺序见方法论第四节：放行字变→人裁没带过来→人审率→切没了/新切出→列分类。
3. **上传**（用户 10-23 定：重跑结果都上传，供需求方和其他会话读取和继续）：
   `GUJI_DATA_TOKEN=$GUJI_DATA_TOKEN_PROD guji products pack push <册> --change <改动名> --report diff-<册> --summary "目的、改了什么、结论" --note "谁、为什么"`
   - 包存 R2（产物不进 Neon 中心库）；标签自动拼 `cv<版本>-c<语料>-g<字形库>-<改动名>`，只增不改，同名拒绝。
   - 默认**不标 main**。标 main（`--main`/`promote`）、写人裁、`guji db push`、发布网站，按红线等用户明说。
   - `push` 会在 `<工作区>/experiments/<册>/<标签>.md` 写实验记录页；记录页提交到 guji-workspace，开草稿 PR。
   - 沙箱产物里有失败页或 `guji status` 有过期，不上传，先查原因。
4. **回报**：给需求方（经协调者）和用户：包标签、`pack fetch` 命令、对比摘要（人审率 A→B、放行字变数、人裁没带过来数）、四样版本、耗时、失败页。
5. **落正式**（需求方认可且用户同意后）：在正式 products 上跑同一条命令，或整册拷回；`guji status` 无过期，`close-check`；再 `pack push --main`。

## 六、A/B 测试怎么跑

先问：变体差在哪？

| 变体差在 | 用什么 | 要点 |
|---|---|---|
| 只在 seed_admit 的参数（开关、阈值） | `guji exp run <实验.yaml> -w $WS --snapshot <基线产物根>` | 上游硬链接共用，各变体只跑 `from: seed_admit`；报告有放行率、送审率、放行错误率及区间、逐格翻转、McNemar、判准；错率只用 `random` 标签，不得拿 `picked` 当错率。变体可各开一进程（`--only`），最后补一次出报告 |
| 切分或更早的步（Step1–4） | 两个沙箱各跑一份，`guji products diff` 对比；或 `scripts/eval_rough_bench.py … --var B.yaml --from row_segment` 对粗校基准 | `exp` 报告只比 seed_admit，对更早的步会报错。切分只看 Step1–4 的变化，不必跑后面 |
| 两份**代码**（分支/提交） | 两个 `git worktree` 各建 `.venv`，各自产物根，`guji products diff` 或 `longrun.sh compare` | `exp` 只能改参数不能换代码；两边 cv 版本要分别记入包标签 |
| 想估全册错率（不是只看翻转格） | `guji exp sample`（scan→cards→page→harvest→estimate） | 要人看图，样本少时区间宽，如实写 |

A/B 规矩：A、B 用同一份上游、同一页集、同一份标签；一次只差一个变量；两个变体的产物都按第五节第 3 步各存一份包（`--change` 名区分，如 `ab-shadow-a`、`ab-shadow-b`）；报告和翻转格抽样页发给需求方判，开不开由人定，A30 不替人定。

## 七、每次运行必须记的

写进实验记录页和 Jira 卡（A34 对比用）：需求单原文；cv 提交号/版本；语料号、字形库号、`db_rev`；册 yaml 与基线的差异；命令全文（含 `--from/--to/--pages/--jobs`）；起止时间与耗时；失败页与原因；产物包标签；对比摘要。失败如实写。

## 八、耗时参考（4 核 15GB，殿本一册约 164–200 页）
Step1–4 约 15 分；Step5–7 约 60 分；仅 seed_admit 约 6–45 分（字块缓存暖时快）；整册约 1 小时 15 分；三册并行峰值内存约 10GB；5-b 备模板索引冷建 45–50 分，用 `pull-rare-index` 几秒；单页全链约 4.5 分。
