# 冻结基线与重跑分级

> 用户 2026-10-18 定（M8，GUJI-567）。管「cv 和字形库一直在更新，已出版本的册怎么办」。
> 时间一律洛杉矶时间。
> 草稿册（还在降人审率的册）的重跑怎么控制、怎么看前后对比，见 [受控重跑方法论.md](受控重跑方法论.md)。

## 一、规矩

1. **到 0.1.0 或 1.0.0 的册登记冻结基线**：快照 `snap/<册>-r<n>`、生成它的 cv 版本与提交、产物 sha。登记在 `team/CV/各册产物cv版本登记.md`（迁移后进本目录）。
2. **冻结册不随 cv 升版重跑。** 默认只登记影响清单（CHANGELOG 里哪些步 `code_hash` 变了）。
3. **已放行的格只增不改。** 要改放行格，走人裁事件＋修订流程（`team/整理/设计/定稿后增量修订.md`），不靠重跑。
4. **告警按原因分级**（原因取 `Engine.stale_reason`）：

| 原因 | 草稿册 | 冻结册 |
|---|---|---|
| 代码变（cv 升版） | 照常过期，增量重跑 | 不报警，只进版本影响摘要 |
| 字形库内容／人裁变 | 过期，重跑 seed_admit | 不报警，计「基线后新人裁 N 条待落地」 |
| 册配置／参数变 | 过期 | 报警 |
| 产物 sha 与快照不符 | — | 报警 |

## 二、重跑四级（先便宜的）

| 级 | 做什么 | 何时 |
|---|---|---|
| L0 | 不重跑，只登记影响清单 | 绝大多数 cv 升版 |
| L1 | `guji exp run`：发布快照作上游，只从受影响的步跑到 seed_admit，出差异报告。不动正式 products，不让任何册过期 | 算法更新后先看影响。**每次 cv 正式发版都出一份**（从下一版起） |
| L2 | 只对有待审格的页重跑受影响步（`--pages`，页集由 `pending_list.py` 或 close-check 待审清单得到）；只合并「待审→机器可放行」的改进 | 算法确实变好、想减少人审时 |
| L3 | 从受影响步起整册重跑，出差异单 | 放行格本身有 bug，极少 |

## 三、为什么这样就够（机制，已核 cv main 代码）

- 指纹＝本步版本＋参数＋本步代码哈希＋直接上游产物 sha（`core/engine.py::fingerprint`），不含上游代码哈希。上游重跑后产物逐字节相同，下游不重算；`status` 的「上游过期」只是显示层。
- Step5 三步有格级复用（`core/reuse.py`）：几何没变的格搬旧记录。但本步代码、参数、checkpoint 或字形库内容一变，复用为空。
- 字形库指纹已是内容指纹（`db_fingerprint`），复制、VACUUM 不变；任何人裁进库都会变 `human_verdicts_fingerprint`，让所有用该库的册的 seed_admit 过期。这是对草稿册应有的提醒，对冻结册是噪声。

## 四、待 CV 工程评估的改动（GUJI 卡见 M8·2.9）

1. `close-check` 1a 冻结模式：比快照 manifest 的产物 sha，不比现行指纹；报基线后新人裁条数。
2. manifest 增 `cv_version`／`cv_commit`（版本号规矩第五节已规划；与 M8·2.5 护栏同源）。
3. `guji archive fetch <tag>`：下载 dataset Release 归档包、核 sha256、解压到空目录。
