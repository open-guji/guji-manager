## 审批规矩（先看）

流程内的常规操作**直接做、做完报结果**，不逐次等批准：落票成人裁事件、出新待审单（含替换线上旧单、触发网站发布）、存产物包、上传书影／雪碧图、触发 proofing-sync、受影响页重跑、book-text 0.x 升版。前提是自动检查都通过。

仍要用户明说：打 v1.0 标签、冻结或解冻、覆盖已发布文本或人裁事件、检查不通过时强行继续、流程之外的写库。

- 只在云端容器里跑，不用用户本机。
- 常用环境变量名：`GUJI_DATA_TOKEN_PROD`（写中心库）、`GUJI_DATA_TOKEN_READ`（只读）、`CELLREVIEW_TOKEN`（读网页投票 KV）、`GUJI_CORPUS_DRIFT`（语料清单漂移时设 `warn`）。

## 一、一轮精校（循环，直到待审清零）

```
投票 → plan（出计划）→ apply（执行）→ 新单上线 → 复审单上推翻
```

1. **投票**：读者在网站精校页投票。票先存在 EdgeOne KV，定时任务 `proofing-sync` 并入中心库。停放模式下票是持续到来的，按增量落票；单册「投完」的判据：全投完，或投过八成且一小时没新票。
2. **出计划**：`scripts/zhengli/proof_cycle.py plan`（cv）。只读：拉库，按**出单版产物包**算锚，落票草稿分「可写／挂起／跳过」三栏并列原因；推翻旧裁、意见不一致、说无字又给字、格位变了的挂起格，出 `recheck.tsv` 送回网站复审。草稿对账是 G0 的依据。
3. **执行**：`proof_cycle.py apply <plan> --hash <哈希>`。按计划原样做：写人裁并消费 → `guji db sync` 推库 → **全册** `seed_admit` 重跑（钉出单版 cv）→ 导出 → 人裁改字进文本，机器改判的退回旧字进复审 → `republish.py issue`（出单门、换单门、传图、存产物包、升 book-text 版本、推库、只发这一章、等发布、读者侧冒烟）。执行时实际内容与计划不符（又来了新票、库 rev 变了）就停，重出计划。
4. **book-text 升版**：精校落票等流程化的小升版直接推 `dev`（先跑 `python3 scripts/local_check.py --dev`；dev 上不提交 `index/texts/`；CHANGES 的 PR 列写 `#TBD`）；每天洛杉矶 03:30 一个 dev→main 的 PR 自动合并。major 升版、大量撤除、改全仓结构或规范、新入库、人手改动，仍单独开 PR 投 `main`，等用户点头。
5. **复审单**：单上写明了旧裁的格，读者投了不同的字即算推翻（事件记 `overrides`）。
6. **改字撞标点／实体锚点**：改了已有标点的册（如 001–010）的字后，只换字时用 `scripts/book-text/punct_redo.py plan` → `apply`；单字替换以外的增删字，推分支交标点项目（A33）。

规矩：

- **旧单上的票先落成事件，再发新单**（`republish.py` 的「旧票先落门」会拒绝）。
- 重跑结果只算提案，不覆盖已发布文本和人裁事件；未冻结册的「变字」一律进待审，不得放宽成「AI 一致就放行」。
- 重跑结果、A/B、评测等往任务库交单：先 `guji_jobs ls` 查重，`export GUJI_JOBS_WHO=A32`，`guji_jobs submit …`（可 `--dry-run`），`guji_jobs show` 看结果。
- 同一批票只让一个会话做；动手前先查中心库有没有该批次的事件。

## 二、冲 1.0（待审清零之后）

1. `text_release.py pin`：锁输入（册 yaml、语料、参照本、格位表、字组、引擎、产物包）。之后别的会话改这几样要先 `check-pin`。
2. 质检：`qa_pick`，挑低置信、易错类别，少于 200 格，只报数（见 [验收标准](验收标准.md) G5、G6）。
3. `text_release.py run`：输入锁 → G0 票账 → G1（看不出 ≤ 待审格 2%）→ G3 close-check（钉住的引擎）→ G3c 读者侧冒烟 → 冻结前能核的出口项。全过则停下。
4. **停点：请用户点头。** 不过就退回 A31／A30，或回到第一部分再走一轮。
5. 用户点头后：`guji freeze register --execute`（冻结包、登记、tag）→ 开 book-text 1.0.0 PR（`local_check.py`）→ 核提交号 → 合并后 `guji exit-check` 全项（G2、G8）。

打 1.0 标签前，PR 里贴提交号核对（两项）：被打标的 book-text main commit；中心库冻结登记的 `cv_commit` 与册 yaml `cv_version` 对应的 tag。对不上就不打标签，先查报告之后谁动了文本。

## 三、冻结之后

- 冻结册默认不解冻，不随 cv 升版重跑（规则与重跑分级见 [冻结基线与重跑分级](冻结基线与重跑分级.md)）。
- 冻结册的机器意见只进团队单，不上公开讨论。
- 1.0 之后的修订走第 5 步「反馈迭代」：意见 → 裁决事件 → `guji opinions revise` → 一批一个 PR。整册解冻要用户明说，重跑后至少升一个 minor，再重新冻结。

## 四、推送去哪

| 产物 | 去哪 | 怎么推 |
|---|---|---|
| 人裁事件、待审单、产物包 | 中心库／R2 | `proof_cycle.py apply`（内含 `guji db sync`、`republish.py issue`） |
| 待审单与图 | 网站（COS） | proofing-sync，`republish.py` 推库后按需触发（云端触发工作流带 `--ref main`） |
| 文本升版 | book-text | 小升版推 `dev`、每日合 `main`；其余开 PR |
| 冻结登记 | 中心库 `feedback/lists/freeze/<册>.jsonl`、R2 冻结包、git tag | `guji freeze register --execute`（用户点头后） |
