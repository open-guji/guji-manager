# 精校全流程：现状梳理与自动化方案（用户 2026-10-22 23:04 PDT 认可，按 P0→P1→P2 实施）

> 写于 2026-10-22 22:50 PDT，A32 精校项目；Jira epic GUJI-637（流程与停点挂 GUJI-730）。
> 依据：第四、五册这一轮（10-20～10-22）的实际经过、M10 交接文档、`规范/1.0发布标准.md`（G0–G8，用户已定一人裁即算）、
> cv `scripts/zhengli/republish.py`、kaiyuanguji-web `.github/workflows/proofing-sync.yml` 与 `iiif-cord-check.yml`、GitHub Actions 运行记录。
> 本文只做梳理和方案：**没有写中心库、没有改任何线上定时任务**，实施等用户逐项批准。

## 0. 一句话结论

慢的根子不在「每天只跑一次」本身，而在**每一步都要一个会话手工串起来，而且每个写库点各要一次「推库」**。
第五册从投完票（10-22 11:59 PDT）到网站上看到扣过已裁的新单（22:37 PDT 手动触发同步），经过了 3 次「推库」、3 个会话、约 10.5 小时；其中真正的机器时间不到 1 小时。
方案的主线是：**把「投完票 → 落事件 → 重跑受影响页 → 升版 PR → 重出单 → 上网站」做成一条命令出一份计划，用户一次确认，按计划原样执行**；
同时把出单前后的几道检查（雪碧图、书影一致、旧票先落）做成自动门，把「容易出错」变成「出错就停」。

## 2. 哪里慢

1. **上网站要等定时或再要一次「推库」。** proofing-sync 定时写的是 14:23 PDT，但 GitHub 的 schedule 常晚 2–5 小时（10-21、10-22 两次都在 17:00 PDT 才跑），还偶尔整晚丢；proofing-sync 也不在 `schedule-watchdog` 的盯防名单里。为了不等，大家改成手动触发（两天 8 次），每次都要用户再说一次「推库」。
2. **每次落票都要搭环境、重算锚。** 新容器装依赖、导字体（约 10 分）、生僻字索引，再重跑有票页到 seed_admit，才知道票落在哪一格。根因是出单时没存那一版产物包（GUJI-730 第 2 条）。
3. **一次投票要经过 4 个写库停点、3 个会话。** 落事件、出新单、传图、发网站各自是独立动作，各自要「推库」，各自由不同会话接手，中间靠人读交接、读草稿。
4. **等人的时间比等机器多。** 用户投完要告诉会话「投完了」；会话出完草稿要等用户回「推库」；PR 要等用户说可以合。机器部分全程不到 1 小时。

## 4. 方案：按优先级

原则：
- **流程化操作不再等用户批准**（用户 10-22 23:04 PDT 定：「尽量减少需要我批准的内容，绝大部分流程化的操作完全不用批准，保护措施已足够」）。一轮精校里的写事件、推库、存产物包、重出单、传图、触发 proofing-sync、0.x 升版 PR 都自动走；保护靠：计划文件＋哈希（写的就是计划里的）、出单门和发布后冒烟（不过就停）、旧票先落门、全部写入可按批次追溯，结果事后报给用户。
- **仍要用户点头的只剩**：打 1.0.0 标签与冻结登记、整册解冻、放宽放行规则（如「AI 一致就放行」）、对外通信；以及任何检查门不过而需要强行越过（`--ack-*`）的情况。
- 只读的步骤（算锚、出草稿、重跑、对比、质检挑格、各项检查）全部可以自动跑，不需要问。
- 检查不过就停，不靠事后发现。

### P0　立刻能缩短等待、风险最小（建议先做）

**P0-1　推库后立即发布到网站，不再等每天一次**
- 做法：cv 的 `republish.py push --sync` 和 `guji cellvotes write`（推库后）末尾，直接触发 kaiyuanguji-web 的 proofing-sync（`workflow_dispatch`，`target=production`、`parts=all`、`dry_run=false`）。会话里也可以用 GitHub 的 `actions_run_trigger` 触发，不必新建令牌。
- 停点：无（用户 10-22 定流程化操作不需批准）。
- 定时保留作兜底；把 proofing-sync 加进 `schedule-watchdog` 的盯防名单（漏跑 6 小时开 issue）。
- 在哪：cv `scripts/zhengli/republish.py`（加 `--publish-web`）；web `schedule-watchdog.yml` 一行。
- 权限：触发 workflow 要对 kaiyuanguji-web 有 `actions:write`。会话里用会话自己的 GitHub 授权即可；若要 cv 脚本自己触发，需一个细粒度令牌，环境变量名建议 `WEB_ACTIONS_TOKEN`（只给 kaiyuanguji-web 的 actions 写）。
- 效果：推库到网站可见从「最晚 24 小时＋」缩到约 3 分钟；不再需要单独的「推库」。

**P0-2　出单门：push 前和 publish 后各一道自动检查**
- push 前（cv，`republish.py push` 内置，不过不推）：
  1. `sprites[]` 齐全：单子里每个 `img.s`、`alt[].g.s` 都在 `sprites[]` 里且有 md5；顺手修 `alt_build.py`／`sprite_pub.attach`，把 `alt-<章>.webp` 登记进去（根治 alt 404）。
  2. 出单工具用 dev 版：重跑钉旧 cv（为了不混进切分变化），但 `republish.py` 这类发布脚本一律用当前 dev，避免再出现「旧脚本漏传图」。在 push 里查 `sprites` 字段缺失就拒绝。
  3. 已裁扣到最新：出单用的人裁截止 rev 与中心库当前 rev 一致，不一致就重扣。
  4. 本册书影一致：对单上涉及的页跑 `check_cord_vs_splits.py`（只读，web 仓脚本，可 pip 直取或复制一份）。
- publish 后（web，proofing-sync 新加一步，G3c）：对刚发布的单，HEAD 每个引用资源必须 200；`/api/cellreview` 读一次本册；不过就在 run 摘要标红并开 issue（标签 `proofing-alert`）。
- 在哪：cv `scripts/zhengli/republish.py`、`alt_build.py`、`sprite_pub.py`（PR 投 dev）；web `nextjs/scripts/lib/proofing-sync-run.mjs`（新加冒烟）。
- 权限：无新权限。

**P0-3　旧票先落门（G0）**
- `republish.py push` 换掉线上单之前，读旧 rev 的票（KV 或 `feedback/lists/web/<书>/<rev>.jsonl`），凡还没落成事件、也没记跳过／挂起的，**拒绝换单**，提示先跑落票；`--ack-unlanded` 才能强行换（要写原因）。
- 这一条直接防住第五册那种漂移。网站侧「此单已换新」提示（GUJI-689）保留，优先级后放。

### P1　把一轮「投完 → 新单上线」串成一条带一个停点的命令

**P1-1　每次出单都存产物包，落票不再重算（GUJI-730 第 2 条）**
- `republish.py push` 时 `guji products pack push`，包标签 = rev（如 `rev-005-r6`）；`cellvotes draft --pack <rev>` 直接用出单版的框当锚。
- 效果：落票从 20–45 分（搭环境＋重跑）变成约 3 分（`from-pack` 实测）；格号天然不漂。
- 停点：无，随出单自动存。

**P1-2　`guji proof cycle`：一轮精校的计划＋执行**
- `guji proof cycle <册> --rev <线上 rev> --plan`（只读，自动跑）：
  1. 读票（KV）→ 用 P1-1 的包算锚 → 出「可写／挂起／跳过」草稿；
  2. 受影响页按人裁重跑、导出、和 book-text main 逐格比（钉出单那一版 cv）；
  3. 按挂起和剩余未审格出下一版单的预览（含扣已裁、P0-2 的出单门）；
  4. 生成计划文件 `plan.json` 和一页中文报告：要写几条事件（批次号）、book-text 改几格升到几版、新单几格、要传哪些图、是否发网站；计划带哈希。
- `guji proof cycle --apply <plan.json> --hash <哈希>`（计划出来后自动执行，不等确认）：按计划顺序执行——写事件并消费 → `guji db sync` → 开 book-text 草稿 PR（跑 `local_check.py`、CHANGES 自动填 PR 号）→ 推新单＋图＋产物包 → 触发 proofing-sync。任何一步的实际内容与计划不符（比如这期间又来了新票、中心库 rev 变了导致扣格不同）就停，重出计划。
- book-text PR 是否自行合并，仍按用户当次说法；新单可以不等 PR 合并就上（新单格号来自同一次导出，与 PR 里的文本一致），或者设成「PR 合了再推单」——这是一个待定项，见 §6。
- 在哪：cv 新命令 `open_guji_cv/cli_proof.py`，把 `republish.py`、`cli_cellvotes.py` 的现有逻辑串起来，不重写。
- 权限：中心库写令牌（`GUJI_DATA_TOKEN_PROD`，已有）、book-text 开 PR（会话 GitHub 授权）、触发 web workflow（同 P0-1）。

**P1-3　什么时候自动开始出计划**
- 选项 A（建议）：用户在线程里说「投完了」，会话直接跑 `--plan` 再 `--apply`，结果事后报。零新基础设施。（用户已选 A）
- 选项 B：定时探测——每 30 分钟查一次各册线上单，若某张单「最后一票已超过 30 分钟、且票数 ≥ 单上格数的 80%」，自动跑一轮。要一个云端定时任务（Claude 的 routine 或 GitHub Action）。A 跑顺后再加。
- 计划出来后自动执行；报告事后发给用户。

**P1-4　云端环境一次装好（GUJI-729）**
- 环境的 setup 脚本里预装 `joblib`、`scikit-learn`、`psycopg[binary]`、`websockets`，设 `GUJI_CORPUS_DRIFT=warn`；字体导入的结果和生僻字索引做成产物包，`guji cellvotes prep` 一条命令取回（约 1 分，而不是 10 分）。
- `joblib`／`scikit-learn` 补进 cv 的 pyproject（小 PR 投 dev）。
- 有了 P1-1 之后，落票本身不再需要字体和重跑；这一条主要为第 11 步（受影响页重跑）提速。

### 不建议做的

## 5. 做完以后，一轮精校长什么样

1. 用户在网站投完，线程里说一句「投完了」（或 P1-3 的探测自动发现）。
2. 会话自动出计划并执行，约 15 分钟后发来一页结果：写了 N 条、挂起 M 格（原因）、跳过 K 条；book-text 改 X 格 0.a → 0.b；新单 Y 格。
3. 此时：事件进库、book-text 草稿 PR 已开（`local_check` 结果在里面）、新单和图已在网站上、冒烟全绿。用户刷新精校页就能接着审新单。
5. 一册审到 G1 清零后，`guji qa pick` 出质检拼图，用户看完，`release check` 出 1.0 报告，再单独确认冻结和打标签。

对比现在：每轮确认从 3 次降到 0 次（只剩 1.0／冻结要确认）；等待从「最晚第二天」降到约 15 分钟；最容易出错的三处（旧票未落就换单、雪碧图漏登、书影不一致）都变成自动拦截。
