# 反馈迭代：目标与入口条件

## 目标
文本版本达到 1.0 之后，仍会发现错字、缺字、标点和专名问题。本步骤管的是：**这些问题从哪来、怎么判、怎么改、怎么发新版、怎么让提出的人看到「已改」，以及怎么保证改动可追溯、可撤销。**

一句话原则：**已发 1.x 的文件不手改。** 任何改动，不论来自读者、算法还是我们自己看出来的，都先成为意见池里的一条意见，再有裁决事件，最后只经 `revise` 工具生成新版本。

## 三个来源，一个入口

| 来源 | 怎么进意见池 | 备注 |
|---|---|---|
| 读者反馈 | 网站「报错」入口 → 每日同步入池（source=web） | 已上线 |
| 算法更新（重跑） | 重跑产物与现行 1.x 逐格比对，每个差异格生成一条机器意见（channel `machine:rerun-<run id>`） | 流程见《步骤》第三节；自动入池仍在建（GUJI-718） |
| 我们自己看出来的 | 手工建意见（source=internal，写明谁、在哪看到、截图块），用 `guji opinions` 命令 | 内部发现也必须建意见，不许直接动文件 |

## 入口条件
- 该册文本线版本已 ≥ 1.0.0（0.x 草稿册的改动走精校，见 [03-精校](../03-精校/)，不走本流程）。
- 该册在中心库有工作区与书 id，意见池里能查到（`guji opinions show … --ws <工作区>`）。
- 你有中心库的读写令牌（取法见 [00-总览/环境与令牌](../00-总览/环境与令牌.md)）。令牌不进仓、不进聊天。

## 不做什么
- 不手改 book-text 里 1.x 版本的 char／cord／punct／entity 文件。
- 不在这里重做切分（C 类，切分变化）：目前不自动处理，转算法项目。
- 不在本步骤里自动合并进 book-text main：合并覆盖线上文本，要用户明确同意（自动合并开关 `auto.merge.enabled` 默认关）。
