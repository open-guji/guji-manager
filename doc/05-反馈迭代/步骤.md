# 反馈迭代：步骤

涉及的仓：`open-guji-cv`（意见池、`guji opinions` 命令、`revise`、人裁事件）、`book-text`（文本与 `CHANGES.md`）、`kaiyuanguji-web`（反馈入口、状态回显）。设计原文：book-text `docs/design/2026-10-已发1x文本修订流程.md`、`2026-10-修订流程自动化设计.md`。

## 一、读者反馈 → 新版本（日常主线）

```
入池 → 初判 → 裁决 → 修订单验证 → 聚批 → 改文本开 PR → 合并 → 记 applied → 回显「已改」
```

1. **入池**：网站每日 Action 把读者反馈和机器检查写进意见池，状态 `new`。
2. **初判**：模型给每条意见定类别、置信度、修订草案和对读者的公开理由。类别：A 改字、B □↔字、B′ 排除框转格、C 切分变化（C 不自动改）。
3. **裁决**：人写裁决事件（采纳／驳回／搁置，驳回要写公开理由，会回显给读者）。**前期**（用户 2026-10-23 定）意见按策略自动结案：置信 ≥ 0.85 的采纳或驳回，事件里 `by=policy:auto-v1`；刷票、用户亲裁、版本漂移、C 类、看不清、置信不足的留着，只在汇总里报。命令：`guji opinions auto decide`；策略在 cv 仓 `config/opinions/rules.json` 的 `auto` 段，改策略走 PR。
4. **验证与聚批**：对**现行文本**干跑 `apply_one`（核 `from`、格号还在、不撞已有格），通过才落修订单；按册聚一批（默认一批 ≤ 50 格）。命令：`guji opinions auto prepare`。
5. **改文本**：`guji opinions revise` 读已采纳意见，改 char／cord，伴生层（标点、实体）跟着改，文本线升版本（≤ 50 处逐处改算 patch，整批规则化改动算 minor，major 要用户点头），写 `CHANGES.md`，每行列意见 id 与事件 id。开 **草稿 PR** 投 book-text；规矩见 book-text `CLAUDE.md`（本地 `local_check.py`、三项校验贴 PR 描述）。命令：`guji opinions auto finish-pr`。
6. **合并**：目前**由用户点头后合并**（自动合并默认关）。合并后 `guji opinions auto finish-merged`：意见记 `applied`（带版本、PR、提交），再 `publish-status` 给网站写状态，读者页回显「已改」。
7. **汇总**：`guji opinions auto digest` 出汇总（新增意见数、自动处理数、待用户定数、PR 数、失败项），前期发在对话里。

每晚洛杉矶 03:23 有定时会话跑 3–7 步（只开草稿 PR，不合并）。

## 二、撤销（改错了）

不 `git revert`，也不手改。对原事件写一条**撤销事件**（写明错在哪），再走一遍修订生成下一个 patch，CHANGES 引撤销事件。历史只追加不删。命令：`guji opinions auto revert|finish-revert`，只能撤已发布的批；若现文已被后来的修订改过，拒绝撤销，需人处理。

## 三、算法提升后重跑已出文本

重跑本身由算法／重跑线程做（交任务库，见 [受控重跑方法论](https://github.com/open-guji-core/ai-team/blob/main/domain/CV/规范/受控重跑方法论.md) 与 [重跑需求与执行规范](https://github.com/open-guji-core/ai-team/blob/main/domain/CV/规范/重跑需求与执行规范.md)）。本流程接手的是**结果怎么落到已发 1.x**：

1. **先比较，再决定。** 新产物与现行 1.x 逐格比，分四类：无变化、新增放行、变化、**被保护格**（有人裁事件或手改的格）。
2. **被保护格默认保留。** 与重跑结果冲突的，逐格报用户，经同意才覆盖。重跑差异摘要里要单列「会冲掉的人裁和手改格」。这条是铁规矩，不因重跑数量大而放松。
3. **其余差异走同一条管线。** 新增放行与变化格各生成一条机器意见，从初判起走第一节；保护格冲突固定 `to_user`，策略不许自动采纳。
4. **覆盖线上文本要用户同意。**
5. **每轮记录度量**：算法版本（cv 版本＋语料号＋字形库号＋产物包名）、受影响册数、四类格数、最终各类处理结果。作为质量度量写入 `metrics.jsonl` 并在 Jira 卡上留一份摘要。

## 四、内部发现

看出错字或疑点，不要直接改文件：`guji opinions` 手工新建意见（source=internal，写谁、在哪看到、截图块），之后与读者反馈完全同路。

## 五、追查「这一格为什么这样」

文本格 → `CHANGES.md` 行 → 意见 id → 裁决事件（谁、何时、理由、证据图块）→ 原始反馈。修订会产出「旧格号→新格号」对照，插格后旧意见靠它迁移。

## 六、存量手改格

1.0.x 里没有事件对应的手改格（盘点见 GUJI-716），要逐格补成事件，或登记为「人工格」（受保护），否则追溯会断。这一项需要用户逐格确认，不自动处理。

## 推送位置小结

| 产出 | 去哪 |
|---|---|
| 文本修订 | book-text，草稿 PR → 用户点头合并 |
| 意见状态、applied、publish-status | 中心库意见池（工作区日志）→ 网站状态回显 |
| 修订批记录、重跑记录、度量 | 意见池 `releases.jsonl`／`runs.jsonl`／`metrics.jsonl` 与 `CHANGES.md` |
| 策略变更 | cv 仓 `config/opinions/rules.json`，PR |
