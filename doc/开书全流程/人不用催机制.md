# 人不用催机制

> 原则（用户 2026-10-31 定）：**人不用去催 Claude；Claude 去叫人审该审的，其余持续推进。**
> 状态：设计 v0。哪些已有、哪些要建，见文末「落地清单」。

## 一、三条硬规则

1. **人审永不阻塞全局**：任何一项人审等待时，Claude 去推进不依赖它的册、页型、步骤（见下「车道」）。只有真正没有别的活可干时才停。
2. **只交真正要人看的**：进人审队列的只有清单里「要人审」写明的类型。凡机检能判的（版框、闸放行率、钉位一一对应、同字验证）一律自己判；判不了才升级。已明确排除的：靠文意区分的字对（己／已／巳、日／曰）不进快审页。
3. **Claude 主动提醒，人只要回应**：队列有未处理项时，Claude 按下面的规则发提醒；人审完（页面后台自动存）或回一句话，流程自动续上，不需要人再说「继续」。

## 二、人审队列

每本书工作区仓根 `开书进度.yaml` 的 `review_queue:` 是权威清单（格式见 [进度表模板](进度表模板.md)）。每项：

| 字段 | 含义 |
|---|---|
| `id` | `<书ID>-<步骤>-<序>` |
| `kind` | `review`（看图点对错）／`decision`（二三选一，带推荐）／`approval`（写共享库、合 PR、对外发布之前的点头）／`action`（人必须自己做的事，如建仓、装 App） |
| `step` | 清单步骤号 |
| `blocking` | 它挡住哪些后续工作；`none` 表示不阻塞任何事（FYI） |
| `size` | 条数／页数，`est_minutes` 预计耗时 |
| `link` | 审阅页 Artifact 链接（或 PR、决定卡） |
| `created_at`, `last_nudged_at`, `nudge_count` | 提醒记账 |
| `status` | `open`／`done`／`dropped` |

**入队前自检**（Claude 必做）：这项是不是只含「自动验不掉」的内容？能压成「一页 ≤ 30 格、默认全对、点不对」吗？能带推荐项吗？不能压的，先继续压，不要把原始材料倒给人。

## 三、不阻塞的推进：车道

同一本书同一时刻有多条车道可以并行，一条停下另一条继续：

| 车道 | 内容 | 被什么阻塞 |
|---|---|---|
| 册间 | 册 A 等快审时，册 B、C 照跑 S5–S9 | 执行机容量 |
| 步间 | 某册 S10 入库后，立刻开该册 S11、S12，不等整书 | 该册 S10 |
| 页型间 | 正文页快审时，目录页单独切分照做 | S5 |
| 书间 | 全唐文、史记各自一条，不互等 | 互不依赖 |

Claude 在每次醒来（见第五节）时，先查队列、再从上表里**找第一条没被阻塞的车道**推进；找不到才进入「等人」状态并在第四节规则下提醒。

## 四、提醒规则（防烦也防遗漏）

提醒走**一个汇总消息**，不是每项一条。内容：这一批有几项、多少分钟能看完、最该先看哪一项（阻塞面最大的）、链接。

| 触发 | 动作 |
|---|---|
| 队列新增项，且 `blocking` ≠ none | 立即发一条汇总（合并近 30 分钟内的新增项） |
| 队列有项但 `blocking` = none（FYI／可选） | 不单发，**搭下一条汇总的便车**，或每天最多一条摘要 |
| 阻塞项 24 小时无响应 | 重发汇总，只列阻塞项，开头写「现在卡住了：…」 |
| 再 48 小时无响应 | 再发一次，并说明**已推进了什么、还剩哪条车道没停**；之后每次间隔翻倍，上限 7 天一次 |
| 所有车道都因人审停住 | 发「全线待人」提醒，一条，列最小可解锁的一项（单项耗时最短、解锁面最大） |
| 人审完成（页面后台出现新存档／回复） | 自动取数→落库→重跑，**不需要人说继续**；之后在下一条汇总里报「已续跑，放行率 x→y」 |

**提醒必须带的**：做完这一项会解锁什么；预计几分钟；链接；默认值（若人不回，Claude 会按推荐项走的，对可撤销的步骤才这么做——不可撤销的步骤（写中心库、合并、对外发布）绝不默认）。

**不提醒的**：机检已过关的步骤的结果，只在汇总里一行带过。

## 五、Claude 怎么「醒着」

流程自己得有时钟，不然只能等人催。用这几个手段（Claude 云会话本身有的）：

- **`send_later`**（单次定时唤醒）：每次做完一轮就给自己约下一次，间隔按第四节递增；长任务（整册重跑 ≈ 1 小时以上）约在预计完成时间之后。
- **`create_trigger`**（周期例程）：每本书一个「开书巡检」例程，每日一次，读 `开书进度.yaml`、查队列、查执行机任务、查审阅页后台有无新存档，然后按第四节发提醒或续跑。
- **审阅页后台**（`ArtifactData`，集合 `review`）：人点一页存一页，Claude 巡检时读到新文档就取数落库。
- **PR／CI 订阅**：book-text 等 PR 的评审意见用 `subscribe_pr_activity` 接。

巡检每次做的事（固定顺序，写进例程提示词）：
1. 读 `开书进度.yaml`；
2. 查正在跑的任务是否完成，完成则做对应的自动判定；
3. 取审阅页后台新存档并落库；
4. 找第一条未阻塞车道推进；
5. 更新 `开书进度.yaml`、必要时发汇总提醒；
6. 约下一次唤醒。

## 六、保证「不丢」

- 进度表在 git 里（工作区仓），会话没了、容器回收了，下一个会话读它就能续上，不靠对话记忆。
- 每个跨会话的结论（过关线校准、用户的一次性批准）写进进度表的 `approvals:` 和经验区，不只放在聊天里。
- 用户的批准要写明**范围**：「提前批准了可以推」只管那一次推送，不自动延伸到下一批；用户说「以后新书入库一律可推」才记成长期批准（`scope: standing`）。
