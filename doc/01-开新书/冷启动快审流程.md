# 新书冷启动：整理本钉位 ＋ 字形快审表

> 2026-10-28 A31 写，实例是《史記》文淵閣本（Book `988g3f0wsu`，GUJI-750）。用户要求另一部书仿照这个进程。
> 适用：**新书自己的字形库是空的、借来的字形（比如殿本刻本）认不了这本书的字体（手写本、坊刻本），但有一份逐列分行的整理本（参校本）**。
> 总代码在 open-guji-cv PR #750（投 dev；合并前用分支 `claude/align-ref-page-pins`）。`模板/` 里的脚本是同一份拷贝，方便不看 PR 也能照做，**以 cv 仓 `scripts/` 为准**。

## 一句话
先让「我们的页」和「整理本的半叶」一一钉死（不靠识别），册里每个格就有了整理本字；再把「借库首位字 ＝ 整理本字」的格按字归并，用一页 30 格、一图一字、默认全对的审阅页让人一眼过完；人审过的格进新字形库，库变了重跑 5a 像素匹配，把剩下的格自动验掉，只把验不过的再交给人。

册01 两轮实测（2026-10-28）：第一轮快审 1,797 格对、13 格不对（61 页）；重跑 5a 后第二轮 309 格（11 页，231 对、78 不对）；最终种子放行 **10,538 / 11,232 = 93.8%**（冷启动前约 65%）。未放行 694 格里 626 格是整理本没有对应字，成因见下「没对上的格」。

早期沙箱估算：锚定页 23→119/143；种子放行 4,412→7,294；快审 1,810 格（61 页）之后，其余 9,422 格的放行从 58%→90%（沙箱，假设全对），5a 判同字的 1,770 格里 1,751 与整理本一致、0 不一致。

## 「页 ↔ 半叶」怎么确定（史记的例子，别书要重新核）
- 册内第 k 页 ＝ 该册叶范围内拆页表的第 k 行（叶升序，同叶 a b c d）。
- 一张图（djvu 一叶 L）分上开（a 右半、b 左半）、下开（c 右、d 左）。
- 殆知阁半叶头 `#@ <djvu>-<id> <叶> h0|h1`：开的 id ＝ `4·(L−5)+下开(0|1)`，h0 ＝右半，h1 ＝左半。
- 实证：整理本 2,859 个开与拆页表 2,859 个上/下开一一对上；没对上的是书名签、衔名、上开无版框单页等整理本没有的叶。
- 找规则的办法：看几张图（先对 3–4 个开，认出哪一页是整理本哪一行），再写脚本全书核对「全部对上、不多不少」才信。

## 快审页的设计（`模板/char_review_grid.tpl.html`）
- 筛选：殿本借库首位字 ＝ 整理本字（两路独立证据一致）的格。
- 每字挑 `--per-char`（3）个**像素匹配度（glyph_match 首位 cov）最高**的格：污渍、残字块 cov 低，自然排在外面。这是用户第一版反馈「有的字里混进别的图」之后改的。
- 一页 30 格，一图一字，**默认全对**，只点不对的（变红）；「本页没问题，下一页」算审完，方向键也能翻页；导出只带已翻过的页，可以分几次审；进度存浏览器 localStorage。
- 结果存后台：`review/b<册>_p<页>` = `{book,page,bad:[格号],ok:[[格号,字]]}`；页面底部「导出」只是备份。
- 页内用 data URI 的小 JPEG，1,810 格约 4 MB；整册 6,000+ 格也不到 20 MB，可以放大 `--per-char`。
- 第一版（一字一行、整字 OK 按钮）太慢，用户否掉了，模板里不再保留。

## 云端环境（会话里要自己补）
- Default 环境的 setup script 在**会话开始时**跑，那时 cv 仓还没 clone，所以会话里自己在 cv 仓建环境：
  `cd open-guji-cv && uv venv .venv --python 3.12 && uv pip install -e ".[console,torch,dev,datastore,shadow,pdf]" --extra-index-url https://download.pytorch.org/whl/cpu --index-strategy unsafe-best-match`。**shadow 缺了 `pipeline` 直接拒跑**。
- `apt-get update && apt-get install -y djvulibre-bin`（djvu 源件解码；不先 update 找不到包）。
- 令牌：会话要有 `GUJI_DATA_TOKEN_READ`（拉库）和 `_PROD`（推库）。
- `guji db pull` 单页 2000 条会 500：用 `pull_small.py`（`PAGE=100`），约十几分钟，后台跑。
- 首次 seed_admit 前 `mkdir -p ~/.guji-data/main/<ws id>/feedback/events`。

## 坑
- 5a 的 `same` 要 cov ≥ 0.996，且**只有借来的条目判 same 会被降成 unsure**；所以人审落进自有库，再 `--force` 重跑，同字格才会升成 same。
- 钉了也对不上的页（表页、考證页、半叶头钉错）：`pin_min_equal_frac`（0.15）兜底，不出标签、note 写明。
- 快审只看抽样格；整字确认的是「这个字是这个字」，其余格靠 5a 验；5a 验不过的才回到人。
- 沙箱实验别污染正式数据：`GUJI_WORKSPACE` 指向复制出来的目录，`GUJI_FEEDBACK_DIR`、`GUJI_GLYPH_DB` 各指临时路径。
- 表页、考證页（版式不是满行）的行闸问题另案，钉位只管对位。

## 给下一部书的清单
1. 有没有逐列整理本？没有的书这套用不了（钉位要它）；退而求其次只能 OCR 对位。
2. 页与半叶的对应规则：重新核对，写一个「一一对应、不多不少」的校验。
3. 借库是谁（殿本？），`workspace.yaml` 的 `glyph_lib.borrow`。
4. 册配置里 `references[0].line_is_column: true`、`corpus` 钉版、`period_prior`。
5. 先在一册上走通（册01 全流程约 12 分钟 ＋ 快审约一小时人时），再铺开。

## 没对上的格（整理本没有对应字）怎么分析
册01 的 626 格不是 Unicode 缺字，主要是页面类型（别直接交人审，正确率不高）：
- **职名页**（官员名单版式，大量空格 ＋ `<臣|>` 小注）：231 格，非正文，先不管；
- **表／稀疏页**：128 格，整行对位走不通；
- **正文页**：223 格。诗页每列切出 22 格而整理本只有 21 字（多一个 `-1` 槽），双行小注页格数几何对不上，坐标对位整列放弃（`coord_fallback` 里有原因）。修法是让坐标对位允许多一格／少一格，会让产物过期，先记着，等样本册跑完统一修。
分析办法：`seed_admit` 未放行且 `align_ref` 没有 `equal/replace` 的格，按页统计，再按整理本半叶头文字归类（职名／表／小注／正文）。

## 做一册还是几册
只做册01 积累偏少（约 2,000 个字形）。**建议下次 2–3 册一起做**：快审页按字归并，同一个字能在不同册、不同位置收到更多写法；剩下的切分修复、人审率提升由这一册自己做，不再是统一问题。
