## 一、它解决什么

5-b 给字形库里没有的字找候选，靠分类头和 embedding 检索两路，两路都「认字」。笔画证据是不认字的一路：

1. 一个小检测网络（只用合成数据训，不含任何书的刻例）在字块上检出六类笔段：横、竖、撇、捺或点、提、折。
2. 候选字的标准写法取自 GlyphWiki 的 KAGE 数据，展开成同样的笔段集合（97,681 字）。
3. 检出笔段和候选骨架逐候选对齐，同类笔段一对一匹配，得一个 0 到 1 的笔画分。

它单独找字不行（首位约 50%），所以只给 5-b 已有的候选排先后，不带新候选。改对的多是同一族里挑码位（内／內、旣／既、扩展区异体）。

## 二、怎么配

册配置（哪一层都能写，见 [册配置.md](册配置.md)）：

```yaml
font:
  stroke_evidence:
    enabled: true      # 缺省 false
    mode: rrf          # rrf（缺省）或 emb
    weight: 4          # 不写取缺省：rrf 4，emb 0.1
```

| mode | 做法 | 实测 |
|---|---|---|
| `rrf` | 笔画分给各路候选的并集排名次，当名次融合里多出来的一路 | 全唐文上这种好 |
| `emb` | 只把 embedding 那一路的前几名按「余弦＋weight×笔画分」重排 | 史記（寫刻體）上这种好：笔画分噪声大，只适合轻推 |

只有三本书的数，哪种接法适合哪类书还不能下结论，按第四节在本书上量。

- 改 `font` 只让该册 5-b（`rare_candidates`）过期，从这一步起重跑。
- 资源在 cv `models/stroke_evidence_v1/`，`guji pipeline model fetch` 会取；缺了只告警一次，结果和没开一样。
- 检出不足 3 段的格、只有一个候选的格不动。
- 每个 worker 多占约 450 MB 内存，每格多约 50 毫秒（CPU）。

## 四、整册对照：全唐文第 020 册

174 页 29,687 格，从 5-b 跑到第 7 步，关／开（rrf 4）各一遍，拿整理本对位字当参照：

- 5-b 首位变了 665 格：原来和整理本一致、被改掉的 494 格，改成一致的 136 格。
- 第 7 步放行 29,653 格、待审 34 格，开关前后都一样，放行字一格没变。

整册里 5-b 首位本来大多就对，笔画分的噪声改错的比改对的多三倍多，第 7 步也没有因此少审一格。所以全唐文不开。
要让它有用，得只在难格上用（5a 没有库例可比、两路首位又不一致的格），这个门控还没做。

## 五、一本书打开之前

先在本书的人裁格上量，再定开不开、用哪种接法：

```bash
# 在 cv 仓里跑；--patches 指本书字形库的原灰度字块目录
python scripts/eval_stroke_evidence.py \
    --samples <dataset>/char-clustering/samples/<本书样本> \
    --patches $GUJI_DATA_HOME/<分支>/<工作区 id>/output/glyph_store/patches \
    --book <册> --corpus <语料文件> --weight rrf:2 rrf:4 emb:0.1
```

看三件事：首位改对比改错多得多（全唐文 rrf 4 是 75 比 12）；unseen 层（类内字）首位不掉；前 5、前 10 不掉。
冻结集达标不够，还要整册对照（做法见 cv `doc/design/5b-笔画证据.md` 第五节）：5-b 首位对整理本改对多于改错，第 7 步待审确实减少。结果登记进 cv `doc/开关登记表.md`。
