# 中心库

> 迁自 ai-team `通用/中心库设计.md`（A20，2026-10-30 按 open-guji-cv dev 核对改写）。
> 表结构与命令细则的源头在 open-guji-cv：`doc/datastore.md`、`open_guji_cv/datastore/schema.sql`。本篇只讲整理时要知道的部分。

## 一句话

人裁、台账、字形库、册配置、`config/`、语料清单这些**多人要写的数据只有一个真源：中心库**（Neon Postgres ＋ Cloudflare Worker ＋ R2）。
2026-10-19 起谁都不再往 `guji-workspace` 的 git 提交数据；`guji-workspace` 冻结在 `6bef1ada`，只用来拿原图。

## 数据放哪

| 放哪 | 放什么 | 怎么进出 |
|---|---|---|
| 中心库 Postgres | 人裁事件、消费台账、锚点、金标、待审单与批次、册 yaml、`workspace.yaml`、`config/**`（含 `book_defaults.yaml`、语料清单、字形库快照清单、钉子账）、字形库各表 | `guji db pull/sync/push` |
| R2 正式桶 | 刻例图、锚图、整理本与大语料文件（按 sha256 寻址，只增不改）；产物包；每日备份 | 随 `db push` 上传；产物包见 [产物包与版本钉](产物包与版本钉.md) |
| R2 实验桶 | 实验分支上新增的图与产物包 | 同上，按分支自动选桶 |
| 本地 | products、cache、`glyph.db`、`glyph-g<N>.db`、字体域 | 由 `db pull` 和起跑前自动重建；不推 |
| git | 原图（guji-workspace）、代码（open-guji-cv、guji-manager） | git |

可重算的东西（`derived`、`cluster_*`、匹配用的 `glyph.db`）不进中心库，本地拉下后自己建。

## 表结构

所有从工作区镜像来的表都带「来源列」：`ws`（工作区 id）、`src_path`（文件在工作区里的相对路径）、`src_line`、`raw`（该行原文）、`rev`（最后一次写这一行的版本号）。
`changes` 每写一行记一条，`rev` 全局递增；**「库版本」就是 `max(changes.rev)`**。

| 表 | 对应的文件 | 说明 |
|---|---|---|
| `workspaces` | `workspace.yaml` | 一行一个工作区（一部书） |
| `books` | `books/<册>.yaml` | 册配置原文进 `raw`，解析进 `doc` |
| `events` | `feedback/events/*.jsonl`、`feedback/vision/*.jsonl` | 人裁事件，只追加 |
| `consumed` | `feedback/consumed/*.jsonl` | 各消费者处理过哪些事件，只追加 |
| `anchors`、`anchor_patches_meta` | `feedback/anchors`、`anchor_patches` | 锚图本身在 R2，表里只存 sha |
| `verdicts` | `feedback/verdicts/**` | 金标 |
| `files` | `feedback/lists/**`、`review/batches/**`、`config/**` 等 | 整文件一行；视图 `lists`、`batches` |
| `corpus_files` | `corpus/**`（整理本） | 表里只记 sha，内容在 R2 |
| `glyph_*`、`glyphs` | `output/glyph_store/**` | 字形库账本；刻例图 `patch_sha` 指 R2 |
| `source_files` | 以上每个文件 | 整文件 sha、行数、末尾换行，核对与还原用 |
| `imports`、`changes` | — | 每次写入的记录与逐行留痕 |
| `freeze_baselines`、`cv_versions`、`snapshots` | — | 登记三表，见下「登记表」 |

`events`、`consumed`、`anchors` 是只追加台账：推送时少了行会被整次拒绝，防止拿旧数据冲掉新人裁。

### 登记表（现状）

三张表已建，但 Worker 还没有写入口，**目前都是空的**。冻结登记的过渡做法：`guji freeze register` 把记录写进数据目录 `feedback/lists/freeze/<册>.jsonl`，随 `guji db sync` 进 `files` 表，以后有写入口照这份文件导入。详见 [产物包与版本钉](产物包与版本钉.md)。

## 读写权限

| 令牌（环境变量） | 能做什么 |
|---|---|
| `GUJI_DATA_TOKEN_READ` | 读：`db pull`、`db status`、`db diff`、取图、取产物包 |
| `GUJI_DATA_TOKEN_EXP` | 开删实验分支、写实验分支、往实验桶存图和产物包 |
| `GUJI_DATA_TOKEN_PROD` | 写正式库（main 分支）、正式桶存包、标 main、`db import` 导回 |

- 命令读 `GUJI_DATA_TOKEN`；只读时可以不设，自动用 `GUJI_DATA_TOKEN_READ`。要写就 `export GUJI_DATA_TOKEN=$GUJI_DATA_TOKEN_PROD`（或 `_EXP`）。
- `db push`／`db sync` 直连 Postgres：有 `GUJI_DATA_PG_DSN` 用它，否则读 `NEON_DATABASE_URL`，在本进程起 443 桥（云会话只通 443）。
- 共享层工作区（`corpus-base`、`glyphlib-*`）普通 push 一律拒绝，只有升级脚本能写；`glyphlib-*` 发布后不可改。
- 令牌和连接串不进仓、不进 Jira、不进聊天。怎么在会话里配见 [环境与令牌](../00-总览/环境与令牌.md)。

## 日常怎么用

```bash
guji db migrate -w <工作区> --dry-run   # 一次性：老工作区的数据挪进数据目录
guji db pull    -w <工作区>             # 中心库 → 本机数据目录；字形库有新内容才重建 glyph.db
guji db status  -w <工作区>             # 分支、rev、落后几条、哪些文件没推
guji db sync    -w <工作区>             # 拉＋合并＋顺带把人裁落进字形库＋推（日常用这个）
guji db push    -w <工作区> [--dry-run] # 只推
```

- **数据目录**：`$GUJI_DATA_HOME/<分支>/<工作区 id>/`（缺省 `~/.guji-data`）。工作区根只留 `workspace.yaml` 和标记 `.central.json`，原图、products、glyph.db 照旧在工作区。
- **push 先比版本号**：该工作区在你的基准 rev 之后有人写过就整次拒绝，先 pull——同 git 的 non-fast-forward。
- **sync 自动合并**：一边改的直接取；两边都改了的只追加台账按行合，其它文件两边都改就停下（`SyncConflict`），什么都不动。要库里的用 `pull --force`，要本地的手工合。
- **sync 顺带落库**（10-24 起）：对还没落进字形库的人裁跑 `glyphdb_admit`、`glyph_audit`，落了再推一次。`--no-admit` 或 `GUJI_AUTO_ADMIT=0` 关。
- 本地有没推的改动时 pull 会拒绝；`--force` 丢掉本地改动。
- `close-check` 第 8 项查「数据目录有没有没推的改动」。

## 实验分支

只比参数、不写库的 A/B 用 `guji exp` 或 `--override`（见 [册配置](册配置.md)），不用开分支。实验要写库（人裁、字形库、字组配置、码位表、语料）时：

```bash
export GUJI_DATA_TOKEN=$GUJI_DATA_TOKEN_EXP
B=exp/GUJI-<卡号>-<小写说明>          # 必须带卡号，最多 63 字
guji db branch create $B [--from-rev N]
export GUJI_DATA_BRANCH=$B            # 之后数据目录、glyph.db、products 都换到这个分支自己的目录
guji db pull -w <工作区>
#   …照常跑…
guji db sync -w <工作区>               # 推到实验分支，新图进实验桶
guji db diff -w <工作区>               # 与 main 逐文件比
unset GUJI_DATA_BRANCH
guji db import --from $B -w <工作区> --dry-run   # 人裁事件导回 main，要正式令牌
guji db branch delete $B               # 用完就删：整个项目最多 10 个分支
```

- 进正式库只有显式的路，不整分支合并：人裁事件用 `db import`（按 id 幂等）；册 yaml、配置这类文件拷到 main 的数据目录再 `db sync`。
- 同一台机器可以一边在 main 上整理、一边在实验分支上试，互不覆盖。

## 版本与钉住

- `db pull --rev N` 钉库版本（该工作区 N 之后没变才放行）。
- 跑批的结果不靠 rev 钉，而靠册 yaml 的三样钉版（`cv_version`、`corpus`、`glyph_pin`），见 [产物包与版本钉](产物包与版本钉.md)。原因：产物在各机本地，同一份内容各机拉到的 rev 不同；本地人裁没推时没有 rev。

## 备份与恢复

- 每日定时会话跑 `python -m open_guji_cv.datastore backup`：全部表导出进正式桶 `backup/<日期>/`，有清单才算完整，保留 30 天。
- 每周日 `restore-check` 恢复到 ci 分支逐表核对。恢复只许打到 main 以外的分支；要从备份救 main，先恢复到新分支核对，再在 Neon 控制台换主分支——**这一步要用户点头**。

## 常见坑

- 云会话直连 5432 不通，`push` 要么设 `GUJI_DATA_PG_DSN` 指本地桥，要么有 `NEON_DATABASE_URL` 让它自己起桥。
- 册 yaml 带 `corpus_dev: true` 推不上去（`push_problems` 拒），先 `guji corpus release`。
- 老版 cv 不认 `corpus_files`，pull 不还原整理本；整理前先确认 cv 版本够新（见 [COMPAT](../../COMPAT.md)）。
- `glyph.db` 只由 `db pull/sync` 和起跑前重建，别手拷别人的 glyph.db：指纹会变、产物判过期。
