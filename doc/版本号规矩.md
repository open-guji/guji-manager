# guji-manager 版本号规矩

> 用户 2026-11-03 定：guji-manager 开始记版本号，**规则和模式一律仿照 open-guji-cv**（cv 仓 `doc/版本号规矩.md`）。本文是照它改写的 manager 版：分支、tag、CHANGELOG、Release、检查脚本都一样；cv 专有的（Step `code_hash`、产物 manifest 的 `cv_version`、册钉版、底库、组合验收）manager 没有，删掉。
> 时间一律洛杉矶时间。

## 一、格式

- 版本号 `MAJOR.MINOR.PATCH`（语义化版本的子集），git tag 写作 `vX.Y.Z`，如 `v0.2.0`。版本号写在两处，必须一致：`pyproject.toml` 的 `version` 和 `guji_manager/__init__.py` 的 `__version__`（`tests/test_version.py` 核）。
- tag 与 cv 同名不同仓，各管各的；口头和文档里提到时写「manager v0.2.0」「cv v0.6.0」区分。不用 `m-v` 前缀（中转站只收 `vX.Y.Z`／`vX.Y.Z-rc.N`）。
- **基线 `v0.2.0`** = 2026-11-03 main `61cc28e`（拆分 P2 第二批之后，Wiki 首版就以它为准）。之前的 0.0.1、0.1.0 只在 CHANGELOG 里有，不补 tag。
- 只用 **annotated tag**；tag 一经推送不改、不删、不挪。要修正就发新 PATCH。
- 预发布用 `vX.Y.Z-rc.N`；rc 只用于验收。
- 三种分支（第三节）：**`dev`** 是日常集成分支，所有 PR 都投它；**`rc/vX.Y.Z`** 是准备发版时从 dev 切出来的测试分支；**`main`** 只接发版（rc 合进来）。tag 打在 main 的发版合并提交上。
- `.github/workflows/release.yml`：推 `vX.Y.Z`／`vX.Y.Z-rc.N` tag 时自动构建 wheel＋sdist＋`SHA256SUMS`，挂到该 tag 的 GitHub Release，没有 Release 就建（rc 标 prerelease）。正式版会先核 tag 与两处版本号一致。

## 二、怎么升版（0.x 阶段）

manager 不进产物指纹、不钉到册，发版不会让任何册过期，所以档位只看「用的人要不要跟着变」。

| 档 | 条件 |
|---|---|
| **MINOR**（0.X.0） | 用法要跟着变的升级：已有命令改了行为或参数、不再兼容；支持的 pipeline 契约范围变了（`COMPAT.md` 改行）；拆分一个阶段做完、整批职责搬过来。**升 MINOR 前先问用户**，还要整体重改 Wiki（第六节） |
| **PATCH**（0.x.Y） | 其余一切：bug 修复、重构、测试、文档、依赖／打包；**新增命令、参数或入口**；从 cv 搬来单个命令；缺省关的新功能；`tools/` 下的书专用脚本 |
| **MAJOR** | 近期不升；到格式与流程稳定、定 1.0 再议 |

- 尽量少升 MINOR。拿不准就按 PATCH，在 PR 描述里写明理由。
- **cv 搬命令过来时**（cv 删一半、manager 加一半）：cv 的 `MIN_MANAGER_VERSION` 要写一个**已发的** manager 版本号。执行机和云端会话经 cv `scripts/ensure_manager.sh` 跟的是 manager **main**（＝最新正式版），manager 这一半只在 dev 上时它们拿不到。所以顺序是：manager 一半合 dev → 切 rc 发一个 PATCH（PATCH 不用问用户）→ cv 那一半再合，`MIN_MANAGER_VERSION` 写这个 PATCH 号。

## 三、分支与发版流程（同 cv）

```
 feat/…、claude/… ──PR──▶ dev ──（准备发版时切出）──▶ rc/vX.Y.Z ──（测完，merge commit）──▶ main ＋ tag vX.Y.Z
                          ▲                               │
                          └────── rc 上的修复合回 dev ──────┘
```

1. **`dev` 是默认的集成分支。** 每个功能在自己的分支上做（`feat/<名>`、`claude/<名>`、`a31/<名>` 均可），从 dev 开出，**PR 目标是 dev**。不直接合 main，也不往 rc 合新功能。文档 PR（`doc/`、`wiki/`）一样投 dev。
2. **合进 dev 的门槛：不破坏现有流程。** dev 随时可能被切出去发版，所以：
   - 新行为缺省关，关着时与改前一样；
   - CI（`.github/workflows/test.yml`）全量测试过；
   - **做了一半也可以合**，只要关着不影响流程；
   - CHANGELOG：dev 顶上有一节 `## [未发版]`，PR 只在这一节下加一行、写明档位；不改版本号。只动 `doc/`、`tools/` 的 PR 可以不写 CHANGELOG。
3. **准备发版时从 dev 切 rc。** 谁觉得一波东西可以发了，就：
   - 在 dev 上提交一次：把 `## [未发版]` 改成 `## [X.Y.Z] - 测试中`，顶上再加一节空的 `## [未发版]`；
   - 从这个提交开 `rc/vX.Y.Z`（版本号按第二节定档；PATCH 不用问用户，MINOR 先问）；
   - 在项目里说一声「manager vX.Y.Z 已切，rc/vX.Y.Z 只收本版修复」。切出之后大家照常往 dev 交 PR，那些改动进下一版。
4. **在 rc 上测试。** CI 全过；有改动的命令在真工作区上跑一遍。发现问题：
   - 修复的 PR 投 `rc/vX.Y.Z`，合进去之后**同一个修复再合回 dev**，不能只修 rc；
   - rc 上**只收本版的修复**，不收新功能。
5. **发版。** 测完没问题：
   - 在 rc 上把 `## [X.Y.Z] - 测试中` 改成发版日期，`pyproject.toml` 与 `guji_manager/__init__.py` 的版本改成 `X.Y.Z`；兼容范围变了同时改 `COMPAT.md`；
   - 开 PR 把 `rc/vX.Y.Z` 合进 main，标题写「发 vX.Y.Z：rc/vX.Y.Z 合进 main」，**用 merge commit（不要 squash）**；
   - **在 main 的这个合并提交上打 `vX.Y.Z`（第 7 条）。打了 tag 才算发完**；
   - 打完跑 `python scripts/check_release_tags.py`（第 9 条），返回 0 再往下；
   - **MINOR 还要整体重改一遍 Wiki**（第六节），发版 PR 里写一行「Wiki 已按 vX.Y 重改」；
   - **把 main 合回 dev**（开 PR 合，带回日期和版本号的改动），之后 rc 分支不再收改动。rc 分支保留不删，版本一律以 main 上的 tag 为准。
6. **main 只接发版。** 平时不直接往 main 合 PR。main 合进来会触发 `wiki-sync`，所以 Wiki 也只随发版更新。
7. **谁来打 tag**：云端会话推 tag 是 403，用中转站：ai-team 仓 `python3 process/tag.py open-guji/guji-manager <main 上合并提交的 40 位 sha> vX.Y.Z "<说明>"`（见 ai-team `通用/协调者通讯.md`「打 git tag」）。中转站只给**默认分支（dev）**上的提交打 tag，所以先把 main 合回 dev（第 5 条最后一步）再打。rc tag 要打的话找 Ops。
8. **合 PR 之前先跑** `python scripts/check_rc_target.py <目标分支>`：目标是 `dev` 返回 0；目标是 rc 时，该版已发（远端有 `vX.Y.Z`）返回 1，不是最新一条 rc 返回 2，还能收修复返回 0；目标是 `main` 返回 4（只有发版 PR 才投 main）。
9. **发版后核对 tag**：`python scripts/check_release_tags.py`（加 `--list` 列出每个版本对应的 main 提交）。它把 main 主线上标题提到 `rc/vX.Y.Z` 的提交认作该版的发版提交：已发却没 tag 的、tag 不在 main 主线上的返回 1。发版 PR 的标题因此**必须写 `rc/vX.Y.Z`**。
10. **按版本找代码**：
    - 某版在 main 的哪个提交：`git fetch --tags origin && git rev-list -n1 vX.Y.Z`；
    - 某个提交最早进了哪一版：`git describe --contains <sha>`，或 `git tag --contains <sha> 'v*'`；
    - 本机装的是哪版：`guji-manager version`（`check --json` 里也有）。

## 四、记录分工：CHANGELOG、Release note

- **`CHANGELOG.md`（仓根）＝完整记录，含 PATCH**：每个版本一节。动代码的 PR 在 dev 的 `## [未发版]` 下加一行；切 rc 时改成 `## [X.Y.Z] - 测试中`，发版时改成日期。
- **GitHub Release**：workflow 自动建、挂附件、一行说明。MINOR 由发版的人在 Release 上补写正文（Added／Changed／Fixed／Removed 分条，每条一行）；PATCH 不写正文。

| 档 | 打 tag | `CHANGELOG.md` | GitHub Release 正文 | Wiki |
|---|---|---|---|---|
| **MINOR** | 打 | 写 | 补写 | 整体重改（第六节） |
| **PATCH** | 打（版本号照升） | 写 | 不写，只有附件 | 不要求动 |

## 五、装哪一版

- 执行机、云端会话：cv `scripts/ensure_manager.sh`／`scripts/zhengli/ensure_manager.py` 每 10 分钟拉一次 manager **main**，所以跟的就是最新正式版。dev 上的改动要发版后才到它们手上（第二节最后一条）。
- 要试 dev：`git -C <manager 目录> checkout dev && git pull`，或 `pip install "guji-manager @ git+https://github.com/open-guji/guji-manager@dev"`。
- 指定一版：Release 附件里的 wheel，或 `pip install "guji-manager @ git+https://github.com/open-guji/guji-manager@vX.Y.Z"`。
- manager 不钉到册、不进产物指纹，换版本不会让任何册过期。

## 六、Wiki（用户 2026-11-03 定，同 cv 第八节）

GitHub Wiki（<https://github.com/open-guji/guji-manager/wiki>）讲「看图懂系统」，命令和参数细节只链到 `doc/`。

1. **PATCH 不要求动 Wiki。**
2. **每升一次 MINOR 必须整体重改一遍**：对照上一个 MINOR 以来的全部 PATCH（`CHANGELOG.md` 各节＋`git log vX.(Y-1).0..HEAD --oneline`），逐页改、补新功能页、重截图；在 Wiki「版本与 Wiki 维护」页记一段，首页版本号改成新的。
3. 这一项算在 MINOR 发版清单里（第三节第 5 条）：发版 PR 里写一行「Wiki 已按 vX.Y 重改」才算发完。
4. Wiki 源文件在仓里 `wiki/`，走 PR 投 dev；合进 main 时 `.github/workflows/wiki-sync.yml` 同步到 Wiki。不在网页上直接改。
