# 第四步　反馈迭代（feedback）

机器和 AI 都判不了的格，每格开一个待审条目放到网站上，由读者对照原图认字；票落成裁定事件，更新 book-text，文本一版一版升，直到 1.0 冻结；1.0 之后继续收网站报错和机器反馈，发 1.x。
怎么做见 Wiki [第四步-反馈迭代](../../wiki/第四步-反馈迭代.md)。命令前缀 `guji feedback`。

```
4a 待审条目上线 ──▶ 读者在网站投票 ──▶ 4b 收单落票 ──▶ 4c 更新 book-text ──▶ 0.x 升版
     ▲                                                                       │
     └──── 出包即收尾（guji land：条目就地对账，没有换单）◀──────────────────────┘
                                                                          │ 达到 1.0 发布标准
                                                                          ▼
                                                        4d 升 1.0、冻结 ──▶ 4e 1.0 之后的反馈（1.x）
```

| 小步 | 做什么 | 主文 | 主要命令 |
|---|---|---|---|
| [4a 待审条目上线](../../wiki/反馈迭代/待审条目上线.md) | 出包即收尾：条目就地对账（没变不动、变了改、新的开、不再待审的关）；网站按章现拼待审单 | [待审条目与裁定事件](../数据库/待审条目与裁定事件.md) | `guji land`、`guji pending`、`swap run`、`online-lists --audit` |

| [4c 更新 book-text](../../wiki/反馈迭代/更新book-text.md) | 换包落 book-text（格号变时走格级对照表）、标 main 后收尾、参校本对比查漏 | [换包落book-text-增删格](../../wiki/反馈迭代/换包落book-text-增删格.md) | `guji feedback swap book-text／finish-merged`、`closeout`、`rekey-cells` |

一轮落票、`guji land` 收尾、重跑受影响页、book-text 升版的常规操作直接做、做完报结果，见 [步骤](../../wiki/反馈迭代/反馈迭代-步骤.md)。

## 要点

- **网站只发 book-text main**；book-text 流程化 0.x 小改直接提交 `dev`，每天洛杉矶 03:30 合一次到 main。
- **裁定一人即算**，不做多人投票或双路复核（落票策略可按会员等级配置，见 [收单](../../wiki/反馈迭代/收单.md)）；重跑结果只算提案，不覆盖已发布文本和已落定的裁定事件。
- **条目发出后格位层尽量别变**（图源 `source_rev`、切分、`manual-cells`）：票和裁定按 `(书, 册, u)` 跟到现格，格已删并的票挂起进复审；定字层（字形库、语料、字组）可以照常升级。格号真变了只走一条路：[换包落book-text-增删格](../../wiki/反馈迭代/换包落book-text-增删格.md)。
- **停放模式**（10-29 起）：用户不再亲自审人审格，大部分册停在 v0.x 等读者投；落票按增量做，不假设「投完了」。
- 主包一天标几次别每次都追：先落票，等本书说这批稳了再标 main。
- 待审条目、裁定事件、book-text 格子三者怎么连，见 [00-总览/待审条目-裁定事件-book-text格子](../00-总览/待审条目-裁定事件-book-text格子.md)；表结构与主流程的基准页是 [数据库/待审条目与裁定事件](../数据库/待审条目与裁定事件.md)。
