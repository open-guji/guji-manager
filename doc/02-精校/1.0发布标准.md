## 2. 条件清单（全部满足才出 1.0.0）

### G0　票、单、事件对账【新提，用户 10-23 同意列为硬条件】（第五册教训）
- **目的**：网页票的格号会漂（第五册：票投在 r4，r5 已换新切分，168 票对不上，靠 `--iou 0.8` 事后救回）。1.0 前必须证明「读者投的每一票都有归宿」。
- **要求**：
  1. 每一份在线待审单上的每张票，都落成了事件，或明确记为：跳过（与已有人裁一致）、看不出（有留痕）、挂起（以新格号进下一版待审单，见 G1）。账要平：票数 = 写入数 + 跳过数 + 看不出数 + 挂起数（第五册样例：168 = 160 + 6 + 2，挂起 0；GUJI-731 里「草稿 141 vs 库里 160」的差异要在出 1.0 前说清）。
  2. 线上没有「过期单」：最新在线待审单的 rev 不早于库里最后一次人裁；单上不含已有人裁的格（第五册 005-r5 还挂着 102 个已投过票的格，真正未审只有 9 格）。
  3. 重跑发新单**之前**，旧单上的票已落成事件（总设计与项目指令已写）；每次出单都存当版产物包（GUJI-730），落票用出单版的框当锚。
- **怎么核**：`guji cellvotes draft` 的「可写／挂起／跳过」三栏对账表入质检报告；`proofing-sync` 的 KV 键数 vs 中心库 `feedback/lists/web/<书>/<rev>.jsonl` 条数。【待建】一条 `guji audit tickets <册>` 把这笔账自动出（现在靠人读草稿）。

### G1　人审覆盖率与待审清零【沿用＋改】
- **要求**（分母 = 最新待审单全部格，分子 = 有处理记录的格）：
  1. 覆盖率 **100%**：每格有处理记录，类型四选一：落字、切坏、非字、看不出。「默认照本」不算过人。`guji audit count <册> --expect <待审单>`：漏审 0、无锚 0。
  2. 「切坏」格必须有去向（重切清单、事件已记 seg_defect），在 decision.json 单列，**不得混进「看不出」**（三阶段 F1）。
  3. 「看不出」允许存在，但每格写一条审阅记录，decision.json `status=open`。**上限：≤ 全册待审格的 2%**（用户 10-23 定）；超了说明书影或切分有系统问题，退回。
  4. 挂起格（锚漂移没写进去的）：必须在下一版待审单里以新格号出现并被审完，或进重切清单；**不能带着挂起格出 1.0**。
  5. 形近字组、高风险通道的格按 G5 另算，不能被「已有人裁」掩盖。
- 第五册现状样例：0.5.0 之后仍有 9 格从未投过票、3 格看不出/切坏、11 个阙文 □，所以尚不满足 G1（见 `A32/册005-剩余人审清单-2026-10-22.md`）。

### G2　发布文本 = 冻结产物导出【沿用】
- 禁止在 book-text 直接改字（用户 10-20 定）；一切改动先是人裁事件（含 manual-cells），重跑涉及页，再导出。
- 核：`guji release diff`（book-text 候选 char.json 与冻结快照导出逐格比，差异 = 0）。【待建】
- 附【沿用】：book-text 的 CHANGES 每行要能追到意见 id／事件 id（`已发1x文本修订流程.md` §三），对不上的变动校验器报红（该规则待建，建议先告警后转红）。

### G3　机器检查全过【沿用＋改】
- close-check 终校档（含 2c、2d）退出码 0；`glyph_audit_gate` 退出码 0，且**体检时点晚于最后一次改库**；排除名单对账（`crop_exclusions.jsonl` 行数 = not_a_char＋damaged 格数）。
- 【改】增加第五册观察到的一条：导出 p3 时 marks 出现重复 id（moyylf4b5bp、mbsahkgdw7k），疑似人裁排除框重跑时重复生成——**marks id 不得重复**，作为 close-check 项（待 cv 查清后建）。

### G3b　书影 / 切分 / 文本三方一致【新提，用户 10-23 同意列为硬条件】（第四册教训）
- **背景**：精校页用 cord 的框画在线上 IIIF 旧图上，cord 重切后没同步 `ops/iiif/siku-zongmu-splits.json` 也没重跑 IIIF，红框就整页错位（册 04/07/09 的拆页书影）。kaiyuanguji-web#572 已加 `ops/iiif/check_cord_vs_splits.py`，每日 `iiif-cord-check.yml` 在跑。
- **要求**：
  1. `check_cord_vs_splits.py --live` 对本册全绿：cord ↔ 裁剪框表 ↔ 线上 manifest 一致（第 1 页书脊签 cord 是一半尺寸，只比长宽比）。
  2. 任何 cord 重切（含 manual-cells）之后，必须**同步 splits 表 + 重跑 IIIF + 按 URL 清 CDN**（图缓存 30 天，不清等于没修）。这一条目前只在记忆里，**要写进 cv 的重切检查清单**【待建】。
  3. 抽查：每册随机 20 页（拆页书至少含每个拆页源各 2 页）打开精校页，红框落在字上；记录页号。
  4. 文本 ↔ cord：char.json 的格数/格号与 cord 一一对应（close-check 已有，列入报告）。

### G3c　读者侧可达性冒烟【新提，用户 10-23 同意列为硬条件】（alt 图 404、cellreview 500）
- **背景**：待审单的相似字雪碧图 `alt-<章>.webp` 没登记进 `sprites[]`，proofing-sync 不传，COS 上 404（册 004–007 都有）；精校页还出现过 `/api/cellreview` 500。两者都不影响数据，但读者看到的是故障，会弃投。
- **要求**（每册出 1.0 前、且每次重出待审单后）：
  1. 待审单 `sprites[]` 含所有被引用的图（含 alt 雪碧图及 md5）；待审单引用的每个资源 HEAD 请求 200。
  2. `/api/cellreview` 对本册读/写各冒烟一次（5 格），返回 2xx。
  3. 页面对加载失败的降级（alt 退回纯文字）保留，但**不能靠降级通过**：404 数 = 0。
- 脚本【待建】：建议放 kaiyuanguji-web `ops/`，和 cord 检查同级，由每日 Action 兼跑。

### G4　已知错单清零【沿用】
- 中心库 `feedback/lists/known-errors.tsv` 对当前文本逐格核，仍是错字的 = 0。有「故意保留」类（册 2 的 3:1 留作测试）。vol01 要能抓出 72:9:9、134:2:9。

### G5　高风险格全看过【沿用】
- 高风险通道（context、rare_ref、iron、match_solo、seal、witness3、coord_fallback 等）全量；形近组全册逐格；跨版本/跨模型分歧全部裁完；非正文页专项通读。每项「判错且没处理」= 0。
- 【新提】第四、五册补充：**alt（相似字）漏登记的格**也算高风险——只要待审单 `alt[]` 与 `sprites[]` 对不上，该格的相似字提示读者看不到，须重出单后再算审过。

### G6　错误率只报数，一人裁即算【改，用户 10-23 定】
- **一人裁即算**：一格只要有一位审校者（目前就是用户本人）裁过，就算「过人」，不要求投票、不要求多人一致。网页上同一格有多票时，取最后一位审校者的裁决，其余留痕。
- **不做双路独立复核，也不做每册约 50 格的校准**（10-20 的 G6 方案暂停：眼下没有两路独立读者，人力只够一人审完）。机器侧已有的信号照常用来挑格：跨版本／跨模型重跑分歧、`glyph_audit_gate` 离群、已知错单；挑出来的格并入 G5 交人审。
- **抽查**：有余力时由审校者随机抽放行格看图，量不限（可以为 0），抽到的数照实报：抽查格数、错数、单侧 95% 上界（1,000 格 0 错 → 0.30%；3,000 格 0 错 → 0.10%）。同一 cv 版本、同一流程的几册可以合并累计。
- **门槛：不设数值门槛，只报数**（用户 10-23 定）。数字写进质检报告和 `review` 记录，由用户看数后决定放不放；数据攒够、人手多了再议门槛和多路复核。
- **错误类型必须记录**【新提】：每个在审校、抽查、机器挑格中发现的错，登记 `类型`（形近替换／异体码位／切分错位/漏切／阙文↔字／标记（夹注、抬头）／非字入文／其他）、`通道`（它是哪条放行通道放的）、`同字组是否已扩查`。写成 `audit` 批次人裁事件，进 open-guji-dataset 新分片 `book-qa/`；汇总表入质检报告。
- **达不到标准怎么办**【新提，用户 10-23 同意】不强行放行：由用户看报告后判定「不放」时，按错误类型退回——切分/书影类退 A30 修，识别/定字类退 A31 重定字（以项目分工为准）；退回单上写错误率、类型分布、样本页号。退回后重新计数，不沿用旧样本。因为不设数值门槛，G0–G5、G7、G8 任一项不过也同样不放行。

### G7　意见台账清零【沿用】
- 意见台账里未处理 = 0。冻结册的机器意见**只进团队单**，不上公开讨论；公众意见经 AI 裁决的算人裁，纯 AI 预判要用户点头（总设计 §0.5 第 3 条）。

### G8　出口动作齐 + 打标签前核对提交号【沿用＋改】
- 沿用 `guji release check <册> --text-dir …` 的全部 ✓：`proofing=false`、文本线 `review` 记录（n、错数、上界、种子、签核人）、decision.json（可以为空）、lacuna 与字一致、yaml 有 `freeze:` 且顶层有 `cv_version`、cv_commit 在某个 tag 上、R2 冻结包 pin 住、中心库 `freeze_baselines`/`snapshots`/`cv_versions` 各有一行、已通知下游。
- 【新提，用户 10-23 定：只核与数据直接相关的两项】**打 1.0.0 标签前的提交号核对**，`release check` 加一栏「提交号」，并把结果贴进 PR：
  1. 将被打标的 book-text main commit（squash 合并后的那个 sha，例：005 的 #219 合并为 e133534）；
  2. 中心库冻结登记的 `cv_commit` 与册 yaml 顶层 `cv_version` 对应的 tag。
  两项对不上：不打标签，先查是谁在报告之后又动了文本（这就是总设计 G2 要防的「手改」）。CHANGES/`review`/质检报告里引用的 sha 属文档记录，**不另设核对项**（用户 10-23 定）；质检报告仍记被检文本 sha，供追查用。

## 3. 版本号与冻结规则

沿用 book-text `docs/VERSIONING.md` 与 `冻结基线与重跑分级.md`，这里只列与 1.0 相关的：

| 事项 | 规则 | 来源 |
|---|---|---|
| 0.x → 1.0.0 | major，**手工**改版本号，附 `review` 验收记录，**用户点头**；`bump_original.py --level major` 报错 | 【沿用】 |
| 0.x 阶段每合一批人裁 | 升 minor（一批 ≤约 50 处改字且位置已知算 patch；成批规则化改动、覆盖率升 ≥10 个百分点算 minor）。第五册 89 格 □→字 一批升到 0.5.0 | 【沿用】 |
| 重跑后 | 至少升 minor | 【沿用】 |
| 1.0.0 后的改动 | 只走修订通道：意见 → 裁决事件 → `guji opinions revise` → 一批一个 PR，patch/minor；不手改文件 | 【沿用】 |
| 冻结 | 出 1.0.0 当天登记冻结（快照 + R2 包 + 三张登记表 + tag），之后册默认不随 cv 升版重跑 | 【沿用】 |
| 解冻 | 默认不解冻；用户明说才整册解冻，重跑后至少升 minor，再重新冻结 | 【沿用】 |
| 冻结册上的未审「变字」 | 未冻结册一律进待审；冻结册机器意见只进团队单 | 【沿用】 |
| 旧定义的 1.0.0（册 002、003） | 照实保留，CHANGES 记「按旧定义」；补走 G0–G8 后算 minor，不算新的 1.0 | 【沿用】 |
| 标点、实体 | 不由本标准管；伴生层 major 不得高于文本线 | 【沿用】 |
| 版本字段 vs 实际 | 出 1.0.0 的 PR 描述写「cv 版本（commit）＋ ws 快照＋事件库 commit」 | 【沿用】 |

【新提】`docs/VERSIONING.md` 第 1 级「可用（精校完）」那一行（「疑难字至少过一遍人审」）比 G1–G8 宽，**出 1.0 时以本标准为准**；定稿后建议同步改 VERSIONING 门槛表与 F-OV 规则，免得两套口径。

## 4. 流程顺序（2026-10-23 晚按审批口径与新工具改，A32）

> 旧写法有「推库」「重出单」两个停点，已过时：用户 10-22 定流程化操作不再逐次批准，靠检查门兜底（项目指令【审批】条）。
> 现在**只有一个停点：打 1.0 标签与冻结**；推翻已有人裁改在网站复审单上由投票人当场做，不再在聊天里问。
> 工具：cv `scripts/zhengli/proof_cycle.py`、`republish.py issue`、`text_release.py`（cv#490、#491）；网站 kaiyuanguji-web#584。

**一轮精校（循环，直到 G1 清零）**——全部直接做，做完报结果：

1. 用户在网站上投票。投完不用说：定时任务跑 `proof_cycle.py status`，全投完或投过八成且一小时没新票即算投完。
2. `proof_cycle.py plan`：拉库、按出单版产物包落票草稿（G0），挂起里能回网站的（推翻旧裁、意见不一致、说无字又给字、格位变了）出 `recheck.tsv`。
3. `proof_cycle.py apply`：写人裁、推库 → **全册** seed_admit 重跑（钉出单版引擎）→ 导出 → 人裁改字进文本、机器改判退回旧字进复审 → `republish.py issue`（出单门、换单门、传图、存包、升 book-text minor 草稿 PR、推库、只发这一章、等发布、读者侧冒烟 G3b/G3c）。
4. 复审单上写明了旧裁的格，用户投了不同的字即算推翻（事件记 `overrides`）。

**冲 1.0（G1 清零之后）**：

5. 冲 1.0 开始时 `text_release.py pin` 锁输入（册 yaml、语料、参照本、格位表、字组、引擎、产物包）。之后别的会话改这几样先 `check-pin`；本册输入变了要退回或重跑后重 pin，共享输入变了冻结时记一笔，不算失败。
6. 抽查（G5/G6，`qa_pick`，挑低置信、易错类别，少于 200 格，只报数）。
7. `text_release.py run`：输入锁 → G0 → G1（看不出 ≤ 2%）→ G3 close-check（钉住的引擎）→ G3c 冒烟 → 冻结前能核的出口项。全过停下。
8. **停点：请用户点头。** 不过就退回 A31／A30，或回到第 1 步再走一轮。
9. 用户点头后：`guji freeze register --execute`（冻结包、登记、tag）→ book-text 1.0.0 PR（`local_check.py`）→ 核提交号 → 合并后 `guji exit-check` 全项（G2、G8）。

仍要用户明说的（不变）：打 v1.0 标签与冻结、解冻、覆盖已发布文本、检查不过强行继续、流程之外的写库。

## 5. 抽样质检方法（汇总）
