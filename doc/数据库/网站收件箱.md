# 网站收件箱（web_inbox）

读者在网站上提交的东西，网站边缘函数直接写进中心库所在的 D1 库，一张表 `web_inbox`。11-21 起票与意见双写，web 0.2.30 起网站原 EdgeOne KV 的内容全搬进来、不再写 KV。
建表与接口在 guji-workspace-data `worker/src/webinbox.ts`；manager 侧读取在 `guji_manager/feedback/web_inbox.py`。

## 表

| 列 | 类型 | 说明 |
|---|---|---|
| `kind` | TEXT | 主键之一，见下表 |
| `key` | TEXT | 主键之一；同 (kind, key) 再写＝覆盖（读者改票） |
| `book` | TEXT | 书 ID，缺省空串；便于按书增量读 |
| `value` | TEXT | JSON 内容 |
| `ts` | INTEGER | 读者端提交时间（毫秒） |
| `seq` | INTEGER | 单调递增，每次写取 max+1；增量读 `after=<seq>` |
| `received_at` | TEXT | Worker 入库时间 |
| `actor` | TEXT | 写入的令牌名 |
| `u` | INTEGER，可空，虚拟列 | 字格永久编号（guji-char v0.6），**册内唯一**：由 `value` 现算，只算 `cellreview`（`value.u`）与 `charfix`（`value.u` 或一段／专名的 `value.u_start`），`value` 不是合法 JSON、不是整数或别的 kind 为 NULL。**线上已加列**（11-27 实查；迁移脚本 guji-workspace-data `d1/migrations/2026-11-25-web-inbox-u.sql`）。现状：`cellreview` 2,868 行里 2,137 行有 u（老票没带），`charfix` 4 行全无 |

索引（线上实查）：`web_inbox_seq (seq)`、`web_inbox_kind_seq (kind, seq)`、`web_inbox_book (kind, book, seq)`、`web_inbox_u (kind, book, u) WHERE u IS NOT NULL`。

**u 只在册内有意义**：同一个 u 在不同册里是不同的格子，拿它去配条目或裁定事件必须带册（`(书, 册, u)`），不能只按 u。票的 `key` 里带册（`cr:i:<书>:<条目>:<voter>` 的条目也带册信息）。

网站在值里带 u 的写法（kaiyuanguji-web #887，双写期键不变）：精校票 `u`；改字 `u`；一段、专名 `u_start`、`u_end`；选字报错（kind `kv` 的 `fb_` 反馈）`cell`、`u`。没有 u 的老单、老文本不带。

## kind

| kind | 装什么 | key 格式 | 写 | 读 | 行数（11-27） |
|---|---|---|---|---|---|
| `cellreview` | 精校票 | `cr:<rev>:…`（旧，单格，按单版本 rev 存）、`cr:i:<书>:<条目>:<voter>`（新，按条目；11-27 约 1,884／2,868 行）。值里仍带 `rev`，按目标要去掉 | 网站 | `guji feedback cellvotes draft`（缺省读这里） | 2,868 |
| `charfix` | 改字意见 | `cf:`单字、`cs:`一段、`ce:`专名，如 `cf:<书>:<册>:…` | 网站 | `guji feedback opinions ingest` | 4 |
| `thread` | 意见下的表态、回复 | `tv:`、`tm:<书>:<册>:…` | 网站 | 网站公开清单、`opinions ingest` | 4 |
| `fixstate` | 整理组对某条意见的处理状态 | `fs:<书>:<册>:…` | 网站 | 网站公开清单 | 1 |
| `pending` | 线上待审单（`guji feedback pending` 出的单经 proofing-sync 写入），太大时切块；**旧的「一章一张整单」形态**，目标由中心库 `pending_current`（一格一条）取代，网站去掉 rev 后下线 | `pd:<书>:<册>` | 网站 | 网站待审页 | 207 |
| `kv` | 其余网站键值，按 key 前缀分：`err_` 错误上报、`fb_` 反馈、`invite:`／`member:` 成员与邀请、`ratelimit:` 限速、`notify:` 通知节流 | 原 KV 的键 | 网站 | 网站自己、管理员 | 81,885（11-27 实查：`err_` 81,840、`fb_` 21、`invite:` 9、`member:` 3、`ratelimit:` 1、`notify:` 1。`err_` 一周从 1.08 万涨到 8.2 万，远超「只留 30 天」应有的量，见下「定期清理」） |

## 令牌

| 角色 | 能做什么 |
|---|---|
| `webinbox` | 只能 `POST /v1/web/inbox`（网站边缘函数） |

实际写入方（`actor`）现全是网站令牌 `kaiyuanguji-web`。key 只许字母数字与 `: _ . | ~ -`，≤200 字；value 是 JSON 对象，≤1.5 MB；一次最多 100 条。
| `web` | 网站令牌（proofing-sync＋边缘函数）：写收件箱、读待审单与公众意见文件 |
| `read`／`main` | 读收件箱（`GET /v1/web/inbox`，manager 用中心库读令牌） |

连法见 [README](README.md) 的 `[webinbox]`（缺省继承中心库）。

## 定期清理

guji-data Worker 每日定时任务（UTC 23:30）调 `cleanupInbox`（`worker/src/webinbox.ts`）：

- `kv` 的 `err_<毫秒>_…` 错误上报：按键里的毫秒只留 30 天（11-22 从 EdgeOne KV 搬来的老报错 `ts` 都是搬家时间，不能按 `ts`）。
- `kv` 的 `ratelimit:*`：`value.exp` 过了就删。
- `pending` 切块 `pd:<书>:<册>~pN`：主单不在、或主单 `parts` ≤ N 的残块删掉。主单本身同键覆盖，每册只有最新一版。

结果记 Workers Logs（`action: webinbox.cleanup`）。

> 11-27 实查 `err_` 有 81,840 行、11-23 是 10,802，增速和清理是否在正常跑待查（没动线上；清理按键里毫秒判，不会误删近 30 天内的）。
