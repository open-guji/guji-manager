# 收单（用户在网站审完一张单之后）

> 现行：2026-11-19（A31，加 `guji collect`）。[粗校迭代流程](粗校迭代流程.md) 第 8 步里「收单」这一段的细则，**收单怎么做以本文为准**。
> 换单的总规矩（首发、主包变了跟单、三条总规矩、坑表）见 [换线上人审单](换线上人审单.md)，本文不重复。
> 来源：全唐文 QTW、殿本 ZM（第一册线手工、第 11–20 册线批量）、史記 SJ 11-17 的收单经验，原始记录见末节；各书时间账汇总在 ai-team `domain/CV/粗校/收单各书汇总-2026-11-18.md`。

## 一、收单是哪一段

用户在网站投完票 → **落票**成人裁 → **推库** → **seed_admit 重放** → **出新单** → **book-text 升版** → **中心库同步** → **发站并核线上 rev**。

两条硬规矩（用户定，不随本文改）：
- book-text 只录首选字；待审原因、候选、人裁事件都在 KV／中心库。
- 线上人审单以最新一轮为准，机器结果不覆盖人裁。

## 二、用哪条路

**没换包、只是用户投完票（最常见）：`guji collect`**（**最低 manager v0.4.68**：v0.4.66 按事件原格号取字、v0.4.67 把旧单条目票按现格重写，都会落错格，别用）。**各书第一次用先 `--dry-run`**，看 `draft/old_sheet.tsv` 和 `落文本.json` 再真跑。人裁定了字就直接写进 book-text，
不等任务库从 seed_admit 重放、不重出单；整个过程只拉库、推库各一次，发站只发这一章并核线上单：

```
guji collect --books auto -w <工作区> --book-text <book-text 检出> [--reviewer sheldon] [--dry-run]
guji collect --books vol20,vol21 …        # 指定册
```

| 步 | 做什么 |
|---|---|
| 0 | `--books auto`：读一遍网站条目票，挑出有票落在还开着的条目上的册（不用自己拉票比） |
| 1 | `db pull` 一次（增量）；读线上单 rev、出单版包 `rev-<rev>`（没有退到 ★main，不用手工 pack fetch＋--cord） |
| 2 | `cellvotes draft --from-kv --items --pack` → `cellvotes write`（批次 `H-web-<册>-<日期>-<rev>`）；落了票的条目自动结案 |
| 3 | 定字票（本次新写的，加上「与已有人裁一致」跳过的——早先落了库、book-text 没跟上的）逐格对 book-text dev 现文：字不同就写人裁的字（去 lacuna），标点 pre_char／专名 text 跟改，升 patch、`local_check --dev`、推 dev（1.x 册推 `swap/<册>-1x` 开草稿 PR）；格框对不上（book-text 不是出单那版切分）、以图代字格不写，报出来等下一轮重放 |
| 4 | `--batch <早先人裁批次>`（可重复）：库里早先写下、还没进 book-text 的人裁也一起落（只认人裁，过绑定表、每格取最新），单上还开着的条目结案 |
| 5 | `db sync` 一次 → proofing-sync 发这次的册（多册一起发一次，`only=` 多章）→ 读 `data.openguji.com/proof/<书>/<章>.pending.json` 核：本次结案的格不再待审 |

- **断点续跑**：`<工作区>/reports/<册>/_collect/<rev>/state.json`，每步记一笔和耗时；停了原命令再跑，做过的跳过；`--fresh` 从头。收完一趟后同一张单又有新票（收单不换 rev），再跑就是新的一趟，旧进度改名留底。
- **网络读超时**（R2／中心库 SSL timeout、StaleBase）：拉库、读票、落票、推库在这一步里重试，不整册重来。
- **发站没成**（云端 gh 没鉴权等）不算失败：单子已进中心库，打印手动触发的参数，每日定时发布兜底；发了以后原命令再跑一次只做核对。
- 不出新单，所以没有「空单要 --allow-empty」「出单版包没存」的问题；挂起票留在单上。
- **旧单上投的条目票**（投票单 rev 不是现行单）不写新事件，只列进 `draft/old_sheet.tsv`：当年落过的由绑定表跟着改绑，没落过的要用当年出单包另落。
- **落哪个字、落哪一格**：一律取 cv `human_chars`（seed_admit 人裁通道同一口径，过绑定表，只认现格 valid／rebound，按改绑后的格号）；算不出来就停、不落 book-text。草稿判「与已有人裁一致」也只认现行生效的人裁，迁移锚／改绑／作废的旧人裁不再挡新票。
- **`--dry-run`**：只拉库、读票、算要落哪些格，book-text 改动提交在 worktree（`<检出>-collect`）不推；不写人裁、不推库、不发站、不留进度。先演练一册看 `reports/<册>/_collect/<rev>/落文本.json`。
- 挂起票、切分票、无字票照旧（看 `draft/report.md`、`held.tsv`、`structure.tsv`）；票的闸不在这里（不出新单）。
- 机器的产物要等下一轮重放才跟上人裁，期间产物字≠book-text 是正常的：人裁最高，重放时 seed_admit 认人裁，自然对上。
- 要换包（标了新 main）的，仍走下表的 `swap run`／`auto_cycle`。

| 情形 | 走法 | 一册耗时（11-17 实测，提速前） |
|---|---|---|
| 一批册、主包已稳 | `guji swap run --books <段> -w <工作区> --book-text <检出>`（非殿本加 `--text-id <书ID>`；册名可写 `001-015`、`01-42`） | 殿本 20 册 3.4 h，每册中位 6 分 |
| 单册、有票 | `proof_cycle.py plan` → `apply`（落票、推库、重放、出单、book-text 一条龙） | 全唐文约 23 分 |
| 单册、没票 | `republish.py issue` | 全唐文 8–10 分 |
| 只落票不改文本 | `guji cellvotes draft --from-kv --items` → `write` → `guji db sync` | 殿本第一册 10–20 分 |

史記到 11-17 还没上过线上单，没有收单实测。它的人裁走卡片审阅页回流（写裁定 → 推库 → 页级重放），见汇总文档。

`swap run` 每 6 册一批：逐册 auto_cycle（plan/apply）→ 批末一次 `db sync` → 这批章一次 proofing-sync（`only=` 多章）→ 逐册核线上 rev，核过的册续跑时跳过。云端会话一个后台命令最多 2 小时，一次交不超过 12 册，被停了照原命令续跑。

## 三、已做的提速（都在现行版本里）

| 改动 | 版本 | 效果 |
|---|---|---|
| `db sync／push` 增量推：只扫只比改了的文件，清单 sha 按 mtime 缓存 | manager v0.4.55（#628） | 殿本有本地改动的 sync 64 s → 8 s |
| `db pull／sync` 增量拉：按 `changes` 表只取库里改了的文件；字形库 instances 这类大台账只补改了的行，整文件 sha 对上才用 | manager v0.4.58（#640） | 殿本 4 个文件远端改动的 sync 97 s → 20 s；结果与整拉逐字节同 |
| 放行格自动回库，对所有书缺省开 | manager v0.4.55（#624） | 不再每册手工回库 |
| book-text 只差码位归一的格留现行字 | manager v0.4.56（#634） | 1.x 不再把 宮→宫 之类改反 |
| `swap run／book-text／finish-merged` 支持非殿本 | manager v0.4.57（#637） | 全唐文、史記可走批量 |
| 落完票新单 0 格也换成空单、升 book-text；auto_cycle 停下的原因取最后一条 ✗ 行 | cv #1643（dev，随下一版 cv） | 殿本 vol08 这类空单不用手工补推；state.json 的 why 写真原因 |
| 读票接口退避重试；push 缺省就 sync 并发站 | cv #1588、#1641 | 不再漏推、少断连重跑 |
| `guji collect`：人裁定字直接落 book-text、不重放不重出单，pull／sync 各一次，断点续跑；`cellvotes write --items` 真的结条目 | manager v0.4.66 | 没换包的收单从 20 分–2 小时（等重放、3–5 次 pull/sync、手工 resolve）降到几分钟 |

增量拉退回整拉的情形：整批导入、变更超过 2 万条或文件超过 400 个、旧数据源、`pull --force／--exclude／--repair-gaps`、新机器。`GUJI_DB_FULL_PULL=1` 强制整拉，`GUJI_DB_FULL_SCAN=1` 强制整扫推。输出里 `scan` 写着这次走的是 incremental 还是 full。

## 四、收单前后要核的

1. **先问用户有没有正在投的册**。`swap run` 遇到正在投的册会判 waiting、不换，这是对的。
2. **看主包标的是谁**：`python -m guji_manager.online_lists --audit <册段> -w <工作区>`。
3. **票的闸**（「还有 N 格的票没落成人裁」）：确认票都已落成人裁才用 `--ack-unlanded-votes "<原因>"`。全唐文 QTW 报 Sheldon 11-17 定这三类（切坏票、看不清票、已有同样人裁）以后一律放行；别的书、别的类型仍要用户点头。
4. **重切过的册**先按新包重建字块缓存，再落票（见换单文档坑表「重切后旧票锚不上」）。
5. **收完核线上 rev**：`curl https://www.openguji.com/api/pending?book=<书ID>&vol=<章>`。proofing-sync 显示 success 不算数。
