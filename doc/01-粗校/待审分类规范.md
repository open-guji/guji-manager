## 一、一条命令

```bash
export GUJI_DATA_PG_DSN=…   # 或只设 NEON_DATABASE_URL（脚本自动起 443 桥）；psycopg、pyyaml 要装在 venv 里
pip install -e guji-manager   # 过渡期还要装 open-guji-cv（用它的连库和字组登记表）
guji-manager pending-stats --out /tmp/ps [--vols 20-50] [--prev 上一份/summary.json]
```
出 `report.md`（总账、各小类的键、分册、数据说明）、`cells.tsv`（每格：册、格号、大类、小类、键、跟进方、处理方式、集中度、成因码）、`summary.json`（下一轮 `--prev` 用，括号里写增减）。全套 99 册约 5 秒，不下产物包、不拉原图。

## 二、数据从哪来（调研结论）

| 要的东西 | 来源 | 说明 |
|---|---|---|
| 每个待审格和它的成因 | 中心库 `files` 表，`feedback/lists/proofing/<文本号>/<册号>.pending.json` | 线上待审单整份在库里；republish 发布时已给每格写 `cause`（成因码 A1…I，`review/causes.py`）和 `cause_detail` |
| 整理本字、文意字、库候选、疑问码 | 同上，格里的 `ref`／`ctx`／`lib_top`／`why`／`occ` | 完整单才有；**vol51–99 的单子是瘦单，只有 cause／cause_detail** |
| 全册格数（算人审率） | `progress.volume.cells_total` | |
| 码位表（判「码位已定」） | `files` 表 `config/codepoints.yaml` | 还没推库的码位用 `--extra-codepoints` 叠 |
| 字组 id | 单子里的 `grp`；没有就按整理本字／文意字／库首选查 cv 字组登记表 | 瘦单查不到，记 `?` |

**不在库里的**（需要包时才下）：seed_admit 的完整证据（文意表 cache_miss、字形判法弃权原因、ctx_garble 细项）、glyph_match 的库候选明细。统计不需要它们；A24 深挖某组时再下包。

**统计的是线上单，不是 ★main 包**：单子落后于 main 时数字也落后。报告里每册列了单子版本、cv 版本、出单时间；落后的先用 `粗校进度填数/sync_online_lists.py` 重出单（标 main 后钩子会自动重出）。

### 已补的字段（pipeline 落库时）
cv（`causes.page_facts`、republish 的 `add_causes`，属生成待审单的一部分，留在 cv）给每格再写：
- `grp`：字组 id（seed_admit 证据里的 `group.id`）
- `refc`：整理本字（单子里没有 `ref` 时用）

下次各册重出单起，Z 类按字组、O 类按整理本有无就能精确分。**还想补、先没做**：文意表缺（`cache_miss`）标记（要写进 seed_admit 证据再带出，改动在 A24 的 flow 里）；遮挡格「框内噪点数」。

## 三、分类体系：8 个大类、24 个小类

判定顺序即成因码优先级（`causes.py`：D → C → A2 → A6/A1/A5/A4/A3/A9 → B → F → E → G → H → I）。一格只进一个小类。

**跟进方**用现在的 Project 名；「处理方式」：`算法／数据可解`＝改算法或补数据后可批量放行（预期，未实测）；`快速确认`＝看一眼的网页卡；`待定口径`＝要 sheldon 定；`只能人审`＝没有自动解。

## 四、跟进流程

1. 每轮重落（或标 main 后单子重出）后，A31 跑一次 `guji-manager pending-stats --prev 上一份`，报告放 `A31/待审分类/`，`summary.json` 留着做下一轮的基线。

3. 「待定口径」（Z2、M2）：A31 出看图表，请 sheldon 定。
4. 「快速确认」（O）：A31 自己做，按印章遮挡卡方案。
5. 「只能人审」：汇总数量交 A32，作为精校工作量。
6. 新增类型：先改 guji-manager 的 `taxonomy.py` 的 SUBS 表和本文第三节，两处同步；guji-manager 的 `tests/test_taxonomy.py` 保证每个小类归属合法。
