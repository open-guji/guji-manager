# 放行格回库：机器放行的缺例字自动补进字形库

> 2026-11-17，字形库自检线。Sheldon 问「纠正过的放行格为什么一直没有回库，尽量做到自动化」后定。
> 代码：`guji_manager/ops/lib_backfill.py`（选格、核验、入库）、`hooks.py::finished`（整册跑完自动触发）、
> `feedback/consumers.py::_admit_backfills`（事件重放）。命令：`guji glyph-db backfill`。
> 相关：[字形快速入库：四层页](字形快速入库.md)（要人看的补字走那里）、[字形图清边与归一](../../参考/字形图清边与归一.md)、
> [5a 分段与形近字组表](../待审原因/near_form_guard/5a分段与形近字组表.md)。

## 一、为什么要有这一步

字形库持续有进项的只有**人裁**：人在控制台或审阅页点了确认，`guji db sync` 顺带落库。**机器放行的格不进库**，
机器来路的刻例以前全靠人手跑批（cv `scripts/book_lib_auto.py`），没有哪一步会自动做，文档里也没有写「每册跑完要回库」。

全唐文的实际后果（2026-11-17 盘点）：

- 机器入库批最后一次是 11-08，之后新跑的册一格都没有回库。
- 120 册里 `rare_ref`、`witness3` 两个通道放行了 6.2 万格、3859 个字，这些字**库里一例都没有**。
- 库里没有的字，5a 相似度模型认不出，只能认成共用部件的别的字：樹认成榭、鄲认成鄆、蟲认成蠱。每一册都要靠
  第 5b 步和第 7 步用整理本纠回来，纠回来的结果又不回库，下一册照旧。
- 七册实测 198 个「5a 自信地认错」里，173 个是这个原因。

所以这不是偶发，是流程缺一环：**放行结果没有回到字形库**。本文这一步把它补上。

## 二、做什么

对一册 `seed_admit` 已放行的格，三步：

| 步 | 规则 | 为什么 |
|---|---|---|
| 选格 | 放行通道是 `rare_ref` 或 `witness3`；放行字是单个汉字；库里该字现有刻例不足 3 例 | 这两个通道都有整理本作证。只补缺例字，量小，每册几百格 |
| | 该格已在库、已有人裁、曾被撤过库的不选 | 人裁为准；撤过的格不让机器再送回去 |
| 核验 | 取管线的字块，按入库同一把二值化与归一，得到库里实际会存的那张图；过字体模型（十万字模板），**模板首位必须就是放行字**；墨量 >0.03 | 见第三节 |
| 入库 | `provenance="auto"`，同时写一条 `confirm` 事件（`actor=model`、`source=auto`、`backfill: true`） | 不算人裁、不进绑定表；可按批次整批撤回 |

每字按 `glyph_match` 覆盖度从高到低试，补够 3 例就停；一格核验不过换下一格，每个空位最多试 3 格。

证据（`admissions.evidence`）里记：事件 id、批次、放行通道、判档、覆盖度，以及核验结果 `verify`
（`tpl_top1`、`tpl_top2`、`tpl_margin`、`ink`）。

## 三、核验为什么这样定

11-11 至 11-13 有过一次教训：「看图加厚」批让视觉模型判「与参校本同形」就按参校本的字入库，分不开讃／讚、廷／延，
而且补的正是不足 5 例的薄字头，库里没有别的例子能反驳。这一批占库 13%，却占后来查实错标的 75%，
已在 11-16 整批撤出重核（ai-team `domain/CV/质检/字形库自检-2026-11-16/`）。

回库要补的同样是缺例字，所以不能只凭「整理本说是这个字」：

- **字体模板首位＝放行字**。字体模型在十万字模板里选一，形近字的另一边也在候选里；图上其实是形近的另一个字时，
  首位多半落在那个字上，这格就不过。整理本（放行字的来路）和字体模型（只看图）是两个独立来源，两边一致才进。
- **核的是库里实际会存的图**。入库时图要再过一遍清边与归一，11-17 修好之前清边会删掉贴边的真笔画
  （[字形图清边与归一](../../参考/字形图清边与归一.md)）。核验用入库后的那张图，图坏了字体模型认不出，自然不过。
- **撤过的格不再进**。库本身不记「撤过不许再进」，这里查 `evictions` 表挡住。

全唐文第一轮实测见第六节。**边界**：字体模板首位只能挡「图上明显是另一个字」，挡不住刻本里两字同形
（毫／亳）和图糊的格；史記 r41 的经验是缺例字的自动入库在只有「三方一致＋覆盖度」时不可靠
（[字形快速入库](字形快速入库.md) 8.7）。所以回库的刻例一律是 `auto` 来路，5b 真刻例原型不认它，人裁同一格时以人裁为准，
每批都可以整批撤回。新书头几册跑完后，抽 100 格以上回库的刻例看图（或先设 `GUJI_AUTO_BACKFILL=0`，不加 `--apply` 手动跑一遍看报告），有错就在 `workspace.yaml` 关掉并按批次撤回。

## 四、怎么用

### 自动：整册跑完就回库

**缺省开**（2026-11-17 Sheldon 定，各书通用）。不要的书在工作区的 `workspace.yaml` 里关掉，或改参数：

```yaml
glyph_lib:
  auto_backfill: false                # 缺省开；写 false 关
  # 或写成对象改参数：
  # auto_backfill: {channels: [rare_ref, witness3], cap: 3}
```

`guji pipeline <册> --pages all` 跑到了 `seed_admit`、没有失败页，收尾时自动对这一册回库，打印一行：

```
  ✓ 放行格回库 067：缺例字的放行格 412，核验过 131 格（74 字），核验不过 9，取不到字块 0；已入库 131 格，库 41879→42010 例、6545→6619 字，批次 auto-backfill-20261117（随下一次 guji db sync 推上中心库）
```

- 这一步排在自动存包之后，只改字形库，不动这一册的产物。
- 只改本机的库。**跑完接着 `guji db sync`**（设 `GUJI_ACTOR`），把事件和新刻例推上中心库。
- `GUJI_AUTO_BACKFILL=0` 临时关。回库失败只提醒，不改跑批的返回码。
- 这一册刚补的字，这一册自己的 5a 结果不会变（已经跑完）；对后面跑的册生效。钉了 `glyph_pin` 的册要出新快照、改钉才用得上。

### 手动：补历史册，或先看报告

```bash
# 只报告，不动库
guji glyph-db backfill -w <工作区> --books 001,002,003 --report 回库报告.json
# 看过报告（picked 是要进的格，rejected 是核验不过的格）再入库
guji glyph-db backfill -w <工作区> --books 001,002,003 --batch qtw-auto-backfill-1117 --apply
guji db sync -w <工作区>
```

机器上要有这些册的原图和产物（`guji source pull`、`guji products pack fetch`），取字块每页约 10 秒；
刚跑完的册字块缓存还在，很快。可选参数：`--cap`（每字补到几例）、`--channels`、`--batch`（缺省 `auto-backfill-<年月日>`）。

### 撤回

```bash
# 在 cv 仓：按批次整批撤，撤库并追加撤回事件，不改旧事件
PYTHONPATH=. python scripts/book_lib_auto.py -w <工作区> --withdraw <批次> --apply
```

单格有错：人在控制台裁这一格，`glyphdb_admit` 会撤掉机器那份、换成人裁；或走体检撤库（`glyph_audit` 事件）。

### 按轮手动回库：钉快照的书（史記，2026-11-18 定）

有的书每轮重跑都钉一版字形库快照（`glyph_pin` 钉 g<N>），字形库由本书的字形库线自己推、自己出快照，比如史記。
这类书**不开自动回库**：自动模式在跑批机上整册跑完就改本机的库，下一册读到的库和钉住的快照对不上，
指纹会漂；补进去的刻例也绕过了「推中心库、出快照、下一轮钉」这一道。做法是：

1. 工作区 `workspace.yaml` 写死 `glyph_lib: {auto_backfill: false}`。manager 换到缺省开的版本时，这一行能保证不被打开。
2. 每轮标 main 之后，字形库线在一台机器上对全书出报告：取现役 main 包（`guji products pack fetch <册>`），
   跑 `guji glyph-db backfill --books 01,…,42 --report …`，不加 `--apply`。
3. 抽查：随机看 100 格以上 `picked`，`witness3` 通道的格全看（整理本与参校本同错的误放只会从这个通道进来）。
   有错就把那几个字从这一批里剔掉（或先人裁），不整批进。
4. `--apply --batch <书>-backfill-<轮次>` 入库，接着 `guji db pull`、`guji db sync --no-admit --with-glyph --dry-run`。
   核 `glyph_exported`、没有删除后再推中心库。
5. 出新快照（`glyph-db snapshot` → `snapshot-upload --pin N --execute` → `pin-verify` → `db sync` 推清单），
   告诉总览和跑批：下一轮钉 g<N>。

史記 40 册 11-18 的报告：缺例字放行格 2,273，核验过 1,229 格（752 字，rare_ref 1,052、witness3 177），
不过 165。看图 266 格（随机 100 格，加上其余 witness3 全看），没有错字，只有 3 格带邻格残笔。已知误放
40:182:2:3（記→訖）不在候选里。

## 五、和 `db sync` 的关系

`db sync` 遇到两边都改了字形库时，取中心库的那份，再让本地新事件重新过一遍消费者。以前的机器入库批直接写库、
事件不可重放，遇到这种情况本地刚入的刻例会丢。回库事件带 `backfill: true` 和字块键，`glyphdb_admit` 认得，
会按事件从字块缓存取图重新进库；缓存里没有字块时报错并留着不记账，到有这一册缓存的机器上再 `db sync` 就落了。
重放不重新核验（核验结果在事件里）。

## 六、全唐文实测（2026-11-17）

全唐文 120 册第一次补库（批次 `qtw-auto-backfill-1117`，Sheldon 批准后入库）：

| 项 | 数 |
|---|---|
| 候选（119 册，每字取覆盖度最高的几格） | 11,468 格 |
| 字体模板首位＝放行字 | 11,208 格（97.7%） |
| 每字补到 3 例后的名单 | 7,889 格、3,614 字，其中原来 0 例的 3,142 字 |
| 入库时对着现库再核，实际入库 | 7,881 格（2 格已有人裁、6 格所属的字已满 3 例） |
| 库的变化 | 37,415 例→45,296 例；有刻例的字 4,321→7,479 |
| 抽样看图 | 两次共 270 格，没有看到错的 |

通道几乎全是 `rare_ref`（7,886 格）。同字多格之间用相似度网络向量互相印证（≥0.6）只多刷掉 10 格，所以没有做进命令。

核验不过的格长什么样（第 009 册整册试跑，225 个缺例字放行格里 8 格不过）：憮的图模板首位是嘸（次位才是憮）、
裒的首位是哀、裹的首位是褁。多数是图上的字与放行字只差一个部件，首位与次位的分差不到 0.003，属于宁可不进的一类。

同一次还把 11-16 因清边丢笔画撤出去的刻例按现格重取图、用同样的门槛重入（批次 `qtw-auto-readmit-1117`）：取到 319 例，过 317 例。

5a 那边的效果以前量过（全唐文 020 册，库清理前后对比）：28 个「5a 自信地认错」降到 2 个。补库之后各册的变化要等重跑后再量。

### 史記、殿本试跑（2026-11-17，只报告不入库）

改缺省开之前，在另外两本书上各取两册量了一遍：

| 书 | 册 | 缺例字的放行格 | 核验过 | 核验不过 | 抽样看图 |
|---|---|---|---|---|---|
| 史記（写本） | 05、20 | 1,492 | 869 格、561 字 | 174（过的比例 83%） | 132 格，没有看到明确的错，1 格拿不准（05:58:3:14a 陣，小字草写，像陴） |
| 殿本 | vol12、vol30 | 904 | 649 格、473 字 | 51（93%） | 132 格，没有看到明确的错，1 格拿不准（vol12:21:3:11 軓，次位軌，分差 0.002） |

## 七、借库的新书：用回库顶替大部分冷启动快审（2026-11-18，脉经）

新书开书时本书库是空的，先借别的书的库跑（`glyph_lib.borrow`）。这时放行的格大多走 `match_ref`
通道：借来的刻例匹配上，且与参校本同字。以前的做法是把这些格挑出来让人快审一遍再入库。脉经第 1 册的实测说明这一步
基本可以由回库代替：

| 项 | 数 |
|---|---|
| 人已快审的格（批 `H-cold-01-1118q`） | 1,189 格，全部是机器当时已放行的格（`match_ref` 1,188、`rare_ref` 1） |
| 人裁与机器放行字一致 | 1,189／1,189 |
| 假设本书库为空，第 1 册回库（加 `match_ref` 通道，每字 3 例）选中 | 1,772 格、818 字（补满 3 例的 412 字）；人快审 1,189 格得到的是 566 字 |
| 核验不过 | 84 格（4.5%），多是码位异体：爲／為、明／眀、内／內、卷／巻、收／収 |
| 选中的格里人也裁过的 | 703 格，放行字与人裁 703／703 一致 |
| 人裁确认的格过核验的比例 | 1,154／1,180（97.8%） |
| 全书 6 册（73,636 格）按现库估算 | 可补 1,333 字、约 2,764 格；本书字头 570 → 约 1,645，覆盖放行格字次 98.2% |

做法：借库的书在 `workspace.yaml` 把 `match_ref` 加进通道。

```yaml
glyph_lib:
  borrow:
    - {from: 995ejelvk0, scope: human+auto}
  auto_backfill: {channels: [rare_ref, witness3, match_ref], cap: 3}
```

已经跑完的册手动补一次（先出报告看一眼 `rejected`，再 `--apply`）：

```bash
guji glyph-db backfill -w <工作区> --books 01,02,03,04,05,06 --channels rare_ref,witness3,match_ref --report 回库报告.json
guji glyph-db backfill -w <工作区> --books 01,02,03,04,05,06 --channels rare_ref,witness3,match_ref --batch <书>-auto-backfill-<MMDD> --apply
guji db sync -w <工作区>
```

要点：

- **要 manager 含「借来的刻例不算本书已有例」的修复**（2026-11-18）。更早的版本数刻例时把借来的也算上，
  脉经本书 570 个字头被数成 4,336 个，回库认为不缺例，一格都不补。
- `match_ref` 只在借库阶段值得加：本书库长起来以后，这条通道的字大多已满 3 例，加不加都一样。
- 核验不过的格留给人。里面多数是参校本用字与底本字形不同码位（内／內），先定码位口径，不要为了入库放宽核验。
- 回库之后还缺例的字头（脉经估约 170 个）再走[字形快速入库](字形快速入库.md)的人审页，量只剩原来的一小部分。
- 回库的刻例是 `auto` 来路，不算人裁，可按批次整批撤回。回库后从 `glyph_match` 起重跑才看得到效果；重跑后送审降多少脉经还没量。
- 试跑脚本与逐格结果在「OCR 研究」Project 线程「加快新书字形库启动」。

## 八、踩过的坑

- **数刻例要连 `instances` 表**。撤库不删 `exemplars` 的行，只数 `exemplars` 会把撤掉的例也算进去，
  撤空了的字被当成「已有例」而不补。cv `scripts/book_lib_auto.py` 数 `n_human`、`n_auto` 时有同样的问题。
- **数刻例不算借来的**（`borrowed` 表，2026-11-18 修）。借库的书不排除借来的例，本书没有的字永远补不进，见第七节。
- **装着的 cv 要含清边修复**（cv #1617，dev 07d4f289 起）。旧版入库时会删贴边笔画，核验会因此多刷掉一些格，不会放错，但白丢。
- **云端跑历史册要边跑边清下载缓存**：`~/.cache/guji-data/sha256` 一百来册会涨到十几 G，盘满之后的册静默失败。
