## 一、为什么要有这一步

字形库持续有进项的只有**人裁**：人在控制台或审阅页点了确认，`guji db sync` 顺带落库。**机器放行的格不进库**，
机器来路的刻例以前全靠人手跑批（cv `scripts/book_lib_auto.py`），没有哪一步会自动做，文档里也没有写「每册跑完要回库」。

全唐文的实际后果（2026-11-17 盘点）：

- 机器入库批最后一次是 11-08，之后新跑的册一格都没有回库。
- 120 册里 `rare_ref`、`witness3` 两个通道放行了 6.2 万格、3859 个字，这些字**库里一例都没有**。
- 库里没有的字，5a 相似度模型认不出，只能认成共用部件的别的字：樹认成榭、鄲认成鄆、蟲认成蠱。每一册都要靠
  第 5b 步和第 7 步用整理本纠回来，纠回来的结果又不回库，下一册照旧。
- 七册实测 198 个「5a 自信地认错」里，173 个是这个原因。

所以这不是偶发，是流程缺一环：**放行结果没有回到字形库**。本文这一步把它补上。

## 二、做什么

对一册 `seed_admit` 已放行的格，三步：

| 步 | 规则 | 为什么 |
|---|---|---|
| 选格 | 乙档通道（`match_ref`、`rare_ref`）：库里该字现有刻例不足 20 例就是候选 | 两路独立证据，入库后被改标的只有 0.15～0.25%（第九节） |
| | 丙档通道（`witness3`、`ref_lib`、`match_replace`、`match_margin`、`coord_fallback`）：该字不足 3 例才是候选，补到 3 例为止 | 整理本为主、库证据弱，只用来救缺例字 |
| | 其余通道不选：文意通道（`context`、`group_flow`、`iron` 等）、只有库自己作证的通道（`match_solo`、`book_knn`、`near_knn`、`consensus_lib` 等） | 没有字形证据，或者是库自己喂自己 |
| | `match_ref` 的格，放行字的库覆盖度领先别的候选字不到 0.003 的不选 | A24 盲读：≥0.003 的 96 格 0 错，以下错 4～10% |
| | 定字时字形对照判「异」（`evidence.verdict == "diff"`）的格不选 | 史记 11-19 全书回库抽查：这类 11 格全是切坏、带框线或邻字的格 |
| | 己已巳、日曰 不选；该格已在库、已有人裁、曾被撤过库的不选 | 按文意定的字组刻形分不开；人裁为准；撤过的格不让机器再送回去 |
| 核验 | 取管线的字块，按入库同一把二值化与归一，得到库里实际会存的那张图；过字体模型（十万字模板），**模板首位必须就是放行字**；墨量 >0.03 | 见第三节。同字异形（整理本写郎、刻的是郞）首位会落在另一形上，不进，符合「按刻形走」 |
| 挑例 | 与这个字已有某例的向量（5a 跨书通用底座 `glyph_sim_base_v1`）相似度 ≥0.975 的算重复，不进 | 重复的例不长本事（第九节实验） |
| | 候选多于空位时，每次挑**离已有例最远**的那个；同一个字每册最多进 2 例 | 让例之间有区别、来自不同的册 |
| | 这个字已有 ≥3 例，而候选与已有例都不像（最大相似度 <0.75）的算离群，不进，记进报告（`reason: far`） | 可能是新写法，也可能是坏图或别的字，留给人看 |
| 入库 | `provenance="auto"`，同时写一条 `confirm` 事件（`actor=model`、`source=auto`、`backfill: true`），证据里记档（`tier`: b／c） | 不算人裁、不进绑定表；可按批次整批撤回 |

每字每册先按覆盖度从高到低排、等距取至多 6 格去核验（高低都取到，才有区别可挑），核验过的再按上面的办法挑。

证据（`admissions.evidence`）里记：事件 id、批次、放行通道、档（`tier`）、判档、覆盖度，以及核验结果 `verify`
（`tpl_top1`、`tpl_top2`、`tpl_margin`、`ink`，和入选时与已有例的最大相似度 `sim`）。

## 三、核验为什么这样定

11-11 至 11-13 有过一次教训：「看图加厚」批让视觉模型判「与参校本同形」就按参校本的字入库，分不开讃／讚、廷／延，
而且补的正是不足 5 例的薄字头，库里没有别的例子能反驳。这一批占库 13%，却占后来查实错标的 75%，
已在 11-16 整批撤出重核（ai-team `domain/CV/质检/字形库自检-2026-11-16/`）。

回库要补的同样是缺例字，所以不能只凭「整理本说是这个字」：

- **字体模板首位＝放行字**。字体模型在十万字模板里选一，形近字的另一边也在候选里；图上其实是形近的另一个字时，
  首位多半落在那个字上，这格就不过。整理本（放行字的来路）和字体模型（只看图）是两个独立来源，两边一致才进。
- **核的是库里实际会存的图**。入库时图要再过一遍清边与归一，11-17 修好之前清边会删掉贴边的真笔画
  （[字形图清边与归一](../../参考/字形图清边与归一.md)）。核验用入库后的那张图，图坏了字体模型认不出，自然不过。
- **撤过的格不再进**。库本身不记「撤过不许再进」，这里查 `evictions` 表挡住。

全唐文第一轮实测见第六节。**边界**：字体模板首位只能挡「图上明显是另一个字」，挡不住刻本里两字同形
（毫／亳）和图糊的格；史記 r41 的经验是缺例字的自动入库在只有「三方一致＋覆盖度」时不可靠
（[字形快速入库](字形快速入库.md) 8.7）。所以回库的刻例一律是 `auto` 来路，5b 真刻例原型不认它，人裁同一格时以人裁为准，
每批都可以整批撤回。新书头几册跑完后，抽 100 格以上回库的刻例看图（或先设 `GUJI_AUTO_BACKFILL=0`，不加 `--apply` 手动跑一遍看报告），有错就在 `workspace.yaml` 关掉并按批次撤回。

### 抢首位核验：只害不帮的字不进（2026-11-18，史記 r80；缺省关）

字体模板核验只管「这张图是不是这个字」，管不了「这个字进库后会不会抢别的字」。史記 g26 回库 9,678 例，
标签看图都对，r80 却多出 987 格待审，其中 482 格是常用字格的库首位被回库进来的形近少见字／异体抢走
（為→蒍、市→巿、榆→揄、悦→悅）。SJ 事后剔掉「只害不帮」的 403 字（959 例，g27）收回大半。
来龙去脉：ai-team `domain/CV/质检/SJ-r80-少见字抢首位-2026-11-18/`（`结论.md`、`A22结论.md`）。

**只看形状的门槛分不开好坏**（A22 与 A31 各自标定，11-18）：回库的字多半库里 0 例（所以才回库），近邻全是别的字。
「形近常用字进前 3、分差 <0.01」这类门槛，拦下害字的比例和拦下有用字的比例几乎一样（A22：拦负例 11% 时误拦正例 7%，
拦 96% 时误拦 89%）。所以闸不看候选的近邻，直接**模拟回库**：

1. 这一册核验过的候选整批加进库（内存里，不动真库），用本册**已放行格**（放行字、字块按入库同一把尺归一）去查，
   kNN 参数取这一册 `glyph_match` 的（`knn_k`／`knn_per_char`／`knn_per_char_top`），与 5a 同口径。
2. 加库前首位＝放行字、加库后首位变成某个新字的格，记在那个新字的 harm 下；加库前首位不对、加库后对了的格，记 help。
3. **harm 有、help 没有的字整字不进**（这一册这个字的几格一起退），报告 `rejected` 里记 `reason: near_common` 和被抢的格键；
   同一次跑后面的册不再选这个字。有 harm 也有 help 的字照进（史記里 蒍 是真姓，压掉会丢真放行）。

代码：cv `clustering/backfill_probe.py`（`BackfillProbe.steal_check`，A22，cv #1679）＋ manager `ops/lib_backfill.py::steal_gate`。
只重匹配新例进得了 kNN 候选池的格，其余格首位不可能变。

**耗时与上限**：每格要取字块图再匹配，一册放行格上万（史記第 02 册 5.2 万）。缺省每册最多回放 8,000 格（等距抽样，报告里
`sampled: true`），`workspace.yaml` 的 `glyph_lib.auto_backfill.steal_cells_max` 改（0＝全部），手动跑用 `--steal-cells-max`。
实测见下面「史記第 02 册回放」。

**缺省关**，要用的书写 `glyph_lib: {auto_backfill: {steal_check: true}}`，手动跑加 `--steal-check`。理由见下面实测：
在真格上它也分不开好坏，又慢。

**闸没做时一定看得出**：装的 cv 没有 `BackfillProbe`（早于 #1679）或核验自己出错时，这一册候选照常进库（不挡回库），
但收尾那行摘要会带「⚠ 0X 没做抢首位核验，候选照常进库：…」，报告 `steal_check` 里记 `skipped`／`error`；
没开闸时摘要带「（抢首位核验未开）」。

**史記第 02 册真放行格回放（A31，11-18）**：r79 现役 main 包的第 02 册放行格，回库例＝g26 里第 02 册的 847 例（588 字），
库＝g26 去掉全部回库例（≈g25），kNN 15/3/10。对照：SJ 剔除单 403 字里本批有 68 字（害），回库有帮的字本批有 47 字（帮）。

| 回放格数 | 重匹配格 | 拦下字 | 其中害字 | 其中帮字 | 取图 | 模拟 |
|---|---|---|---|---|---|---|
| 抽 8,000 | 4,660 | 32 | 7／68 | 5／47 | 13 分 | 9 分 |
| 全册 50,677 | 29,779 | 85 | 17／68 | 8／47 | 13 分 | 27 分 |

（两组同机并跑，单跑会快一些。）全册回放也只拦下四分之一的害字，同时拦下六分之一的帮字。
原因：r80 的害是**全书**的格在**新一轮**里变成新待审，一个字害的格多是一两格、散在各册；按册回放、
又以「首位被抢」而不是「新增待审」计，看到的害既少又不同。所以缺省关。

**更准的做法是事后按轮核**（命令 `guji glyph-db backfill-audit`，见 [回库事后核](回库事后核.md)）：下一轮跑完，比上一轮新增的待审格和新放行格，
按库首位归到回库字上，「只害不帮」的字撤库。SJ 出 g27 剔 403 字就是这样，收回约 690 格新待审，只丢 1 格帮；
命令在史記 r79→r80 上算出的撤库单与 SJ 手工单重合 396 字。全唐文库刻例回放被回库字抢首位只 0.3%（1 万例抽样；史記 2.9%）。

## 四、怎么用

### 自动：整册跑完就回库

**缺省开**（2026-11-17 Sheldon 定，各书通用）。不要的书在工作区的 `workspace.yaml` 里关掉，或改参数：

```yaml
glyph_lib:
  auto_backfill: false                # 缺省开；写 false 关
  # 或写成对象改参数：
  # auto_backfill: {cap: 20, thin: 3, per_book: 2, dup_sim: 0.975, far_sim: 0.75, match_ref_gap: 0.003,
  #                 channels: [match_ref, rare_ref, witness3, ref_lib, match_replace, match_margin, coord_fallback],
  #                 tier_c: [witness3, ref_lib, match_replace, match_margin, coord_fallback],
  #                 steal_check: true, steal_cells_max: 8000}
```

`channels` 是收哪些通道，`tier_c` 是其中哪些算丙档（只补不足 `thin` 例的字）；`cap` 每字最多几例，`per_book` 每册每字最多进几例。
以前在 `workspace.yaml` 里写死了 `cap: 3` 或 `channels` 的书不会自动换成新缺省，要按新规矩就把那两项删掉。

`guji pipeline <册> --pages all` 跑到了 `seed_admit`、没有失败页，收尾时自动对这一册回库，打印一行：

```
  ✓ 放行格回库 067：缺例字的放行格 412，核验过 131 格（74 字），核验不过 9，取不到字块 0；已入库 131 格，库 41879→42010 例、6545→6619 字，批次 auto-backfill-20261117（随下一次 guji db sync 推上中心库）
```

- 这一步排在自动存包之后，只改字形库，不动这一册的产物。
- 只改本机的库。**跑完接着 `guji db sync`**（设 `GUJI_ACTOR`），把事件和新刻例推上中心库。
- `GUJI_AUTO_BACKFILL=0` 临时关。回库失败只提醒，不改跑批的返回码。
- 这一册刚补的字，这一册自己的 5a 结果不会变（已经跑完）；对后面跑的册生效。钉了 `glyph_pin` 的册要出新快照、改钉才用得上。

### 手动：补历史册，或先看报告

```bash
# 只报告，不动库
guji glyph-db backfill -w <工作区> --books 001,002,003 --report 回库报告.json
# 看过报告（picked 是要进的格，rejected 是核验不过的格）再入库
guji glyph-db backfill -w <工作区> --books 001,002,003 --batch qtw-auto-backfill-1117 --apply
guji db sync -w <工作区>
```

机器上要有这些册的原图和产物（`guji source pull`、`guji products pack fetch`），取字块每页约 10 秒；
刚跑完的册字块缓存还在，很快。可选参数：`--cap`（每字最多几例）、`--channels`、`--batch`（缺省 `auto-backfill-<年月日>`）。

### 一次性补历史册：先各册出候选，再统一挑

每字每册只进 2 例，是为了让例散在各册。历史册一次补齐时，各册取图核验很慢但互不相干，分两步做：

```bash
# 第一步（可以几台机器、几个进程并行，每册一个文件）：只选格、核验，候选连图存下，不挑不入库
guji glyph-db backfill -w <工作区> --books 001,002,003 --pool 候选/
# 第二步（一台机器、一次）：合起来按册序统一挑有区别的例；先不加 --apply 看报告，再入库
guji glyph-db backfill -w <工作区> --from-pool 候选/ --report 回库报告.json
guji glyph-db backfill -w <工作区> --from-pool 候选/ --batch <书>-auto-backfill-<MMDD> --apply
guji db sync -w <工作区>
```

第二步对着现库重查「已在库／已有人裁／撤过库」，所以两步之间库变了也不会重进。第二步不做抢首位核验（`steal_check` 开了也不生效），补完按轮事后核（第九节）。

### 撤回

```bash
# 在 cv 仓：按批次整批撤，撤库并追加撤回事件，不改旧事件
PYTHONPATH=. python scripts/book_lib_auto.py -w <工作区> --withdraw <批次> --apply
```

单格有错：人在控制台裁这一格，`glyphdb_admit` 会撤掉机器那份、换成人裁；或走体检撤库（`glyph_audit` 事件）。

### 按轮手动回库：钉快照的书（史記，2026-11-18 定）

有的书每轮重跑都钉一版字形库快照（`glyph_pin` 钉 g<N>），字形库由本书的字形库线自己推、自己出快照，比如史記。
这类书**不开自动回库**：自动模式在跑批机上整册跑完就改本机的库，下一册读到的库和钉住的快照对不上，
指纹会漂；补进去的刻例也绕过了「推中心库、出快照、下一轮钉」这一道。做法是：

1. 工作区 `workspace.yaml` 写死 `glyph_lib: {auto_backfill: false}`。manager 换到缺省开的版本时，这一行能保证不被打开。
2. 每轮标 main 之后，字形库线在一台机器上对全书出报告：取现役 main 包（`guji products pack fetch <册>`），
   跑 `guji glyph-db backfill --books 01,…,42 --report …`，不加 `--apply`。
3. 抽查：随机看 100 格以上 `picked`，`witness3` 通道的格全看（整理本与参校本同错的误放只会从这个通道进来）。
   有错就把那几个字从这一批里剔掉（或先人裁），不整批进。
4. `--apply --batch <书>-backfill-<轮次>` 入库，接着 `guji db pull`、`guji db sync --no-admit --with-glyph --dry-run`。
   核 `glyph_exported`、没有删除后再推中心库。
5. 出新快照（`glyph-db snapshot` → `snapshot-upload --pin N --execute` → `pin-verify` → `db sync` 推清单），
   告诉总览和跑批：下一轮钉 g<N>。

史記 40 册 11-18 的报告：缺例字放行格 2,273，核验过 1,229 格（752 字，rare_ref 1,052、witness3 177），
不过 165。看图 266 格（随机 100 格，加上其余 witness3 全看），没有错字，只有 3 格带邻格残笔。已知误放
40:182:2:3（記→訖）不在候选里。

## 五、和 `db sync` 的关系

`db sync` 遇到两边都改了字形库时，取中心库的那份，再让本地新事件重新过一遍消费者。以前的机器入库批直接写库、
事件不可重放，遇到这种情况本地刚入的刻例会丢。回库事件带 `backfill: true` 和字块键，`glyphdb_admit` 认得，
会按事件从字块缓存取图重新进库；缓存里没有字块时报错并留着不记账，到有这一册缓存的机器上再 `db sync` 就落了。
重放不重新核验（核验结果在事件里）。

## 七、借库的新书：用回库顶替大部分冷启动快审（2026-11-18，脉经）

新书开书时本书库是空的，先借别的书的库跑（`glyph_lib.borrow`）。这时放行的格大多走 `match_ref`
通道：借来的刻例匹配上，且与参校本同字。以前的做法是把这些格挑出来让人快审一遍再入库。脉经第 1 册的实测说明这一步
基本可以由回库代替：

| 项 | 数 |
|---|---|
| 人已快审的格（批 `H-cold-01-1118q`） | 1,189 格，全部是机器当时已放行的格（`match_ref` 1,188、`rare_ref` 1） |
| 人裁与机器放行字一致 | 1,189／1,189 |
| 假设本书库为空，第 1 册回库（加 `match_ref` 通道，每字 3 例）选中 | 1,772 格、818 字（补满 3 例的 412 字）；人快审 1,189 格得到的是 566 字 |
| 核验不过 | 84 格（4.5%），多是码位异体：爲／為、明／眀、内／內、卷／巻、收／収 |
| 选中的格里人也裁过的 | 703 格，放行字与人裁 703／703 一致 |
| 人裁确认的格过核验的比例 | 1,154／1,180（97.8%） |
| 全书 6 册（73,636 格）按现库估算 | 可补 1,333 字、约 2,764 格；本书字头 570 → 约 1,645，覆盖放行格字次 98.2% |

做法：借库的书在 `workspace.yaml` 把 `match_ref` 加进通道。

```yaml
glyph_lib:
  borrow:
    - {from: 995ejelvk0, scope: human+auto}
  auto_backfill: {channels: [rare_ref, witness3, match_ref], cap: 3}
```

已经跑完的册手动补一次（先出报告看一眼 `rejected`，再 `--apply`）：

```bash
guji glyph-db backfill -w <工作区> --books 01,02,03,04,05,06 --channels rare_ref,witness3,match_ref --report 回库报告.json
guji glyph-db backfill -w <工作区> --books 01,02,03,04,05,06 --channels rare_ref,witness3,match_ref --batch <书>-auto-backfill-<MMDD> --apply
guji db sync -w <工作区>
```

要点：

- **要 manager 含「借来的刻例不算本书已有例」的修复**（2026-11-18）。更早的版本数刻例时把借来的也算上，
  脉经本书 570 个字头被数成 4,336 个，回库认为不缺例，一格都不补。
- `match_ref` 只在借库阶段值得加：本书库长起来以后，这条通道的字大多已满 3 例，加不加都一样。
- 核验不过的格留给人。里面多数是参校本用字与底本字形不同码位（内／內），先定码位口径，不要为了入库放宽核验。
- 回库之后还缺例的字头（脉经估约 170 个）再走[字形快速入库](字形快速入库.md)的人审页，量只剩原来的一小部分。
- 回库的刻例是 `auto` 来路，不算人裁，可按批次整批撤回。回库后从 `glyph_match` 起重跑才看得到效果；重跑后送审降多少脉经还没量。
- 试跑脚本与逐格结果在「OCR 研究」Project 线程「加快新书字形库启动」。

## 八、踩过的坑

- **数刻例要连 `instances` 表**。撤库不删 `exemplars` 的行，只数 `exemplars` 会把撤掉的例也算进去，
  撤空了的字被当成「已有例」而不补。cv `scripts/book_lib_auto.py` 数 `n_human`、`n_auto` 时有同样的问题。
- **数刻例不算借来的**（`borrowed` 表，2026-11-18 修）。借库的书不排除借来的例，本书没有的字永远补不进，见第七节。
- **装着的 cv 要含清边修复**（cv #1617，dev 07d4f289 起）。旧版入库时会删贴边笔画，核验会因此多刷掉一些格，不会放错，但白丢。
- **云端跑历史册要边跑边清下载缓存**：`~/.cache/guji-data/sha256` 一百来册会涨到十几 G，盘满之后的册静默失败。

## 九、每字 20 例、来路分档（2026-11-18 重定）

Sheldon 11-18：「所有的字只要是确定了的，不管是人审的还是自动放行的，按说都应该入库；每个字可以有一个 10～20 的上限；
尽量不要录完全重复的字形；人审进来的和自动放行的要区别对待。」当天定上限 20。分析文档：
<https://claude.ai/artifact/LN3nvvLX7Gsa2kRnfmm56L>；脚本与中间结果在「OCR 研究」Project 文件夹 `字形库入库规矩-2026-11-18/`。

### 现状（全唐文，11-18 拉库）

库 46,060 例、7,678 个字头：正好 3 例的 2,998 个，3 例及以下占 64%。12 册（003、010…110）34 万放行格里
`match_ref` 占 91.25%、`rare_ref` 2.2%、`match_replace` 1.7%、`ref_lib` 1.1%、`witness3` 0.5%。3 例及以下的字头管着约 5% 的格。
「3 例」是三处叠出来的：回库 `CAP = 3`；只收 `rare_ref`、`witness3`；粗校验收线把「可信 ≥3 例」当成够了。

### 各来路有多可信

中心库事件日志里 2.5 万条机器入库事件，对照其后的人裁、改标事件：

| 来路 | 入库 | 后来改标或人裁改字 | 错的是什么 | 档 |
|---|---|---|---|---|
| `match_ref` | 12,588 | 31（0.25%） | 全是 郞→郎 一类同字异形的码位 | 乙 |
| `rare_ref` | 11,630 | 18（0.15%） | 搆→構、遙→遥、升→𦫵，也是码位 | 乙 |
| `witness3` | 298 | 8（2.7%） | 含真错字 治→洽 | 丙 |
| `ref_lib` | 135 | 15（11%） | 全是 𬽠→變 一个字头 | 丙 |
| `match_margin` | 64 | 2（3%） | 𬽠→變 | 丙 |
| `group_flow` | 32 | 6（19%） | 𨽾→隷、䧟→陷；没有字形证据 | 不进 |

另：人审例库内被旗标 1.48%，多数是字定对了、图是残的（11-16 自检，切分残缺 18 例里 13 例来自人审）；「看图加厚」批（视觉模型判
与参校本同形）旗标率 5.41%、占查实错标 75%，已整批撤。「改标」是被人或自检发现的，只能当下限，但各来路之间的高低是清楚的。

结论：主要通道跨字的真错极少，风险在**同字异形按整理本码位进库**和**图坏**，所以自动入库的关键是刻形核验（字体模板首位＝放行字），
通道只是第一道筛子。

### 上限与挑例

现库例数 ≥28 的 186 个常用字，每字留出 8 例当考题（1,488 题），其余全库每字最多留 N 例，看考题的最近邻是不是本字
（向量用没见过全唐文的跨书底座 `m_lobo_m_no_qtw`）。表里是首位认错的比例：

| 每字上限 | 随机挑 | 挑互相最不像的 | 挑最像的 |
|---|---|---|---|
| 1 | 5.31% | 1.95% | 1.95% |
| 3 | 2.33% | 1.41% | 2.35% |
| 5 | 1.52% | 1.14% | 1.95% |
| 10 | 1.14% | 0.81% | 1.68% |
| 15 | 0.76% | 0.47% | 1.55% |
| 20 | 0.56% | 0.40% | 1.14% |
| 不限 | 0.40% | 0.40% | 0.40% |

3 例不够；挑有区别的 5 例抵得上随机的 10 例；20 个有区别的例追平不限量，所以上限定 20、挑离已有例最远的。
局限：考题是库里已有的例，偏干净，只考了常用字。

### 人审与自动的区别

| | 人审 | 自动（乙、丙） |
|---|---|---|
| 库里的标记 | `human` | `auto`，证据里记档、通道、批次、核验结果 |
| 5a 找候选、训练模型 | 用 | 用 |
| 当「人确认过」的证据（5b 真刻例原型、近形决胜、共识升档计数） | 算 | 不算 |
| 同一格两边不一致 | 以人审为准 | 让位 |
| 出了问题 | 逐格复审 | 按批次整批撤 |

### 还没做的

- **满额置换**：满 20 例后来了更高档或更有区别的例，换掉最低档里最重复的那个；丙档例在这个字甲乙档够 3 例后退出。
- **人审入库的图像体检**：墨量、切分残缺、清边不变式不过的只记字、不存图。
- **形近字对分类器（5a.3）同意**：放行字在分类器里有对子的，还要分类器判成这个字。等有书打开 `pair` 再接。
- **抢首位**：`match_ref` 也回库后常用字的例变多，预期会缓解史記 r80 那种少见字抢常用字首位，但没有量过。A31 的建议是按轮事后核：
  下一轮跑完把新增待审按库首位归到回库字，只害不帮的撤库（史記 g27 的做法）。抢首位核验开关保留、缺省关。
