# 设计：待审条目化（待审单从「一册一张」拆成「一格一条」）

> 状态：**草案，待 sheldon 评审**（2026-11-10，A31）。
> 起因（sheldon 11-10）：「待审单要以一册为整体吗？能不能拆成每个格子，它的单独的待审都是独立的……以后能不能让我比较独立地去改、撤下或修改某一个格子的待审情况？」
> 已定节奏：先做单格原地改（cv #1355 `republish.py edit-cell`，已合 dev），再做本设计。
> 背景总纲：[待审单-人裁事件-book-text格子](待审单-人裁事件-book-text格子.md)。本设计只改「待审单」这一样，不动 book-text 格子和人裁事件的含义。

## 一、现状：为什么一格要动就得整张换

一张单 `feedback/lists/proofing/<书>/<章>.pending.json` 带一个 `rev`（如 `001-r13`）。下面四样都绑在 rev 上：

| 绑在 rev 上的 | 怎么绑 | 后果 |
|---|---|---|
| 网站的票 | KV 按「书＋rev＋格」存，`/api/cellreview?rev=…` | 换 rev 后旧票在网站上不显示；所以换单前必须先把旧票全部落成人裁（`votes_gate` 拦） |
| 落票算锚 | 要用出单那一版的产物包 `rev-<rev>` 才知道票投在哪块图上 | 每张单都要存一个产物包 |
| 图 | 字块图／雪碧图按 rev 整包出、整包传 R2，单上每格引用雪碧图坐标 | 新加一格没有图，只能整张重出 |
| 网站 | 精校页一次读一整张单；发布按章 | 改一格也是整章重发 |

所以「撤一格」「改一格说明」「加一格复审」都要走一整轮 prep → push → 发布（5–10 分钟，还要先落完票）。
`edit-cell`、`add-alt`、`add-sprites` 是在这个框架里打的补丁：只能动已有格、不换 rev。

## 二、目标

1. **一格一条，互相独立**：增、撤、改某一格，不碰别的格，不换整张单，立刻生效。
2. **票永远对得上图**：票记「投在哪块图上」，不依赖单子版本；换不换单都不丢票，不再需要「换单前落完票」这道闸。
3. **机器跑一轮只动有变化的格**：没变的格（同一块图、同样的原因和候选）保持原条目、原票、原图。
4. **人能单独操作**：撤下、放回、改说明、加复审、改首选字提示，都对单格生效，并留记录。
5. **「一册的待审单」仍然存在，但只是查询**：这册当前所有开着的条目。人审率、待审原因统计都按它算。

## 三、条目（待审条目）

### 1. 身份

条目的键是**图块**，不是格号：`条目 id = <书 id>:<册>:<图块指纹>`。
图块指纹用现有人裁锚的口径（原图上的框＋字块图哈希，cv `feedback/anchor.py`、`doc/design/15-人裁锚定与重切后重绑定.md`）。
格号 `页:列:格` 只是条目当前的位置（`cell` 字段，可变）。重切以后：

- 同一块图（锚对得上）→ 同一条目，只改 `cell`；
- 图变了（切开、合并、框挪动超过阈值）→ 旧条目「撤（重切）」，新图块开新条目，旧票挂在旧条目上，按人裁重绑同样的规则处理。

### 2. 字段

| 字段 | 含义 |
|---|---|
| `id` | 条目 id（见上） |
| `book`／`vol`／`cell` | 书、册、当前格号 |
| `state` | `open`（待审）、`withdrawn`（撤下）、`resolved`（已有人裁，留作显示）、`superseded`（重切换了新条目） |
| `why` | 待审原因码（`pending_reason`，可多个，主因在前） |
| `cand` | 候选：`stale`、`ref`、`lib_top`、`alt`、`ctx`；`first`（首选字，现算后存一份） |
| `img` | 字块图 URL（按图块内容寻址，一格一张，不再进按 rev 的雪碧图）；`ex`（同字例子图） |
| `note`／`prior`／`recheck` | 卡片头说明、旧人裁、是否复审格 |
| `dian`／`sent` | 点校倾向字、带标点句子（只提示） |
| `src` | 谁开的这条：机器哪一轮（产物包标签）、人（谁）、脚本（哪个） |
| `ver` | 条目自己的版本号，每改一次 +1 |
| `log[]` | 每次改动 `{ver, op, by, at, why}`：开、改原因、改候选、撤、放回、改说明、已裁 |

### 3. 存放

- 真源：中心库一张表 `pending_items`（主键 `id`，`(book, vol, state)` 建索引），改动只追加 `log`、更新当前行，**不整张替换**。
- 本机镜像：数据目录 `feedback/pending/<书>/<册>.jsonl`（一行一条），随 `guji db sync`。
- 网站：按条目发布（一条一个 KV 键，或按页分片），改一条只发一条。精校页按「册＋state=open」列出。

## 四、票

- 票的键从「书＋rev＋格」改成「**条目 id＋条目 ver**」，票里另带投票时看到的图块指纹。
- 落票不再需要 `rev-<rev>` 产物包：条目 id 本身就是锚。
- 条目改了候选或说明（ver 变），已有的票照旧有效；只有图变了（换新条目）才需要重绑，规则同人裁重绑：绑不上就进复审。
- 没有「换单」这件事，`votes_gate` 去掉；票随时可落。

## 五、谁怎么改条目

| 谁 | 动作 | 做法 |
|---|---|---|
| 机器跑完一轮（标 main 后） | 按新包逐格比：新出现的待审开新条目；不再待审的标 `resolved` 或撤；原因、候选变了的只改字段（ver+1）；没变的不动 | 取代现在的 `republish prep/push` 整张出单；`guji pending reconcile <册> --pack <标签>` |
| 人（sheldon、各书项目） | 撤下、放回、改说明、加复审格、改首选字提示 | `guji pending withdraw/restore/note/add <条目或格号>`，网站后台也可点 |
| 人裁落票 | 条目标 `resolved`，记是哪条事件 | `cellvotes` 落票时顺带 |
| 撤库重审、点校、seg 自检等 | 开复审条目，`src` 写来源 | 各自调同一个接口，不再拼 `--recheck` 清单 |

规矩：

1. **人工撤下的条目，机器不会自己放回**：下一轮机器仍判待审时，条目保持 `withdrawn`，在统计里单列「人工撤下」，要人放回。
2. **条目改不改，都不动 book-text**：book-text 什么时候改仍按总纲的逐格规则，看的是人裁和机器放行，不看条目。
3. **人审率**＝这册 `state=open` 的条目数 ÷ 全册格数（与现在口径相同，只是不再从文件数）。

## 六、迁移

1. **第 0 步（已做）**：`edit-cell` 在现有单上单格撤下、放回、改说明（cv #1355）。
2. **第 1 步：条目表与 reconcile**（manager）：建 `pending_items`；从现行各册线上单导入（一格一条，`src=import:<rev>`）；
   `guji pending reconcile` 按新包更新条目；同时**照旧导出一份整张的 `pending.json`**给网站用（从条目现算），网站先不动。
3. **第 2 步：图按内容寻址**（manager／cv sprite）：一格一张图存 R2，条目引用；雪碧图只作网站加速用的派生物。
4. **第 3 步：网站按条目读、票按条目记**（kaiyuanguji-web，A32）：精校页、`/api/cellreview` 改键；旧票按「rev＋格 → 条目 id」一次性迁移。
5. **第 4 步：去掉 rev 与换单闸**：`republish prep/push`、`proof_cycle` 改为 reconcile＋落票；`votes_gate`、`rev-<rev>` 产物包退役。

每一步都可单独上线，前一步不依赖后一步；第 1 步做完，人工单格操作就已在条目上生效（网站经整张导出看到）。
