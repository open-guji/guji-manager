# 待审单、人裁事件、book-text 格子：三样东西和它们的关系

> 2026-11-10 A31 整理（sheldon 要求：「所有的设计应该都是围绕这三个东西来」）。
> 本篇是这三样东西的**总纲**：含义、范围、关键信息、谁写、多快变，以及它们之间怎么转。
> 细节规范各有真源（文末「真源」一节），细节以真源为准；**三者的分工与规矩以本篇为准**，别的文档与本篇冲突时改别的文档。

## 一、一句话

| 东西 | 一句话 | 回答的问题 |
|---|---|---|
| **book-text 格子** | 这一格**现在显示什么字** | 读者看到什么 |
| **待审单** | 这一格**还要不要人看、为什么、有哪些候选** | 人该看哪几格 |
| **人裁事件** | 人**说过**这一格是什么（只追加的历史） | 人定了什么 |

三者是同一个「格」在三个地方的三种身份：**现状、问题、答案**。
机器（pipeline）只是第四方：它每轮产出新结果，按下面的规矩改写「现状」和「问题」，但永远不改「答案」。

## 二、各自是什么

### 1. book-text 格子（现状）

- **含义**：读者在网站阅读页、下载文本里看到的那个字。每格**只录一个字**，就是首选字（已定的字，或待审格的首选字）。
  待审的字和别的字**看起来一样**，不带任何标记（11-09 定）。
- **范围**：book-text 仓里每册每章的 `NNN.char.json` 的每个格（坐标在 `NNN.cord.json`，规范化在 `NNN.norm.json`；
  标点、专名是挂在格上的伴生层 `punct`／`entity`）。正文、夹注、抬头、图片格都是格。
- **关键信息**（只有这些）：
  - `a`：格位 `页:列:格[a|b]`（章内；夹注 a/b 右先读；负数是超框抬头）
  - `c`：字
  - `lacuna: true`：**只给真阙文**（审过定阙）。□ 只表示真阙文，**待审 ≠ 阙文**
  - `guess_c`：阙文的推测字（括注用）
  - `fig`：图片格
- **不录**：待审原因 `pending_reason`、候选、置信度、人裁记录、`decision.json`、点校的 `assumed`（11-09 起全部不进 book-text，校验 F-OV-16、F-OV-05 会拦）。
- **谁写、多快**：只在**换包（出新单／重导出）、修订、点校入标点**时改，每次升文本线版本、写进 git 提交（`版本记录:` 行）。
  **原则是少改**：一次改字就是一次 book-text 提交、一次升版、可能一次标点重投影。

### 2. 待审单（问题）

- **含义**：一册当前**还要人看**的格的清单，每格带「为什么要看」和「看什么」。它是**状态快照**，每出一版单整体替换。
- **范围**：一册（一章）一张，带版本号 `rev`（如 `001-r13`）。包含三类格：
  1. 机器没放行的格（`review: pending`）；
  2. 复审格（`recheck: true`）：人裁过但要再看的——机器推翻了人裁、旧人裁绑定失效、**撤库重审**（撤库的格，不论册在哪个版本）、别处发现的疑点；
  3. 已人审、留在单上显示结果的格（`review: human`）。
- **住哪**：真源在**中心库** `feedback/lists/proofing/<书 id>/<章>.pending.json`（随 `guji db sync`）；
  网站精校页读的是它发布出去的副本（proofing-sync → 网站存储／KV）。平时说「待审信息在 KV」指的就是这一路：中心库待审单 → 网站。
- **关键信息**：
  - 单头：`rev`、`cv_version`／`cv_commit`（出单用的产物）、`source_rev`（页表版本）
  - 每格：`cell`（同 book-text 的 `a`）、`review`、`why`（待审原因码，`pending_reason` 枚举，真源 manager `review/pending_reasons.yaml`）、
    候选（`stale` 旧人裁失效前的字、`ref`／`refc` 参校本、`lib_top` 字形库前几名、`alt` 相似字、`ctx` 上下文）、
    `recheck`／`note`／`prior`（复审说明与旧人裁）、`img`／`ex`（字块图、同字例子）、`dian`／`sent`（点校倾向字、带标点句子，只提示）
  - **首选字** `first_choice` 由候选现算：`stale` → 参校本 → `lib_top[0]` → `alt[0]` → `ctx`（与网站候选排序一致）
- **谁写、多快**：每轮出单（`republish.py prep/issue`、换单 `proof_cycle`）整张重出；**改单不动 book-text**。

### 3. 人裁事件（答案）

- **含义**：人对某一格（或切线、版框、列……）下的判断。**只追加、不改不删**；同一格多条按「后到覆盖」取最新。
- **范围**：全工作区；定字类（`confirm` + `payload.v`：定字／切坏／不是字／阙／图片格）是和格子直接相关的那部分，
  另有切分类、字形库体检（撤库、白名单）等。网站精校页的投票先进 KV，再落成事件（`cellvotes`，H-web 批次）才算人裁。
- **住哪**：中心库 `events` 表（stream=`events`）；本机镜像 `feedback/events/<batch>.jsonl`。
  **不算人裁**的另有：看图结论（stream=`vision`）、大模型裁定（stream=`rulings`，键是前后文窗口，不是格号）、点校旁路笔记（`feedback/notes`）。
- **关键信息**：`id`、`ts`、`kind`、`target.key`（`册:页:列:格`，**带册号**）、`target.anchor`（当时那块图的位置与指纹）、
  `payload.v`／`shape`（定的字）、`reviewer`、`payload.pending_reason`（当时为什么待审，只作统计）。
- **谁写、多快**：人随投随写；脚本只通过 `EventLog.append` 写。规范见 cv `doc/formats/人裁事件规范.md`。

## 三、它们怎么连在一起

### 1. 同一个格的三个键

| 位置 | 键 | 例 |
|---|---|---|
| book-text | `a` = `页:列:格` | `100:4:17b` |
| 待审单 | `cell` = `页:列:格`（同 `a`） | `100:4:17b` |
| 人裁事件 | `target.key` = `册:页:列:格` ＋ `target.anchor` | `vol02:100:4:17b` |

格号是**切分的输出编号**，不是字的身份。重切以后同一个编号可能指向别的字，所以人裁靠 **锚**（原图上的框＋图块指纹）
重新绑定到现在的格（绑定表 `feedback/bindings/`，cv `doc/design/15-人裁锚定与重切后重绑定.md`）。
绑不上的人裁记「失效」，那一格回到待审单当复审格（`stale` 带旧字），**不会把人裁用到别的字上**。

### 2. 一格的生命周期

```
            机器跑一轮（产物包）
                   │
          ┌────────┴─────────┐
          ▼                  ▼
     放行（定字）         没放行／要复审
          │                  │
          │           进【待审单】（why、候选、首选字）
          │                  │
          │             人在网站投票
          │                  │
          │             落成【人裁事件】
          │                  │
          │        下一轮：人裁通道放行（人裁永远最高）
          ▼                  ▼
        【book-text 格子】按下面的规矩改或不改
```

### 3. book-text 什么时候改、改成什么（换包／重导出时逐格判）

优先级：**人裁 > 机器新结果 > 现行文本里的机器旧字**。机器可以挑战人（出复审格），不能覆盖人。

| 情形 | book-text | 待审单 |
|---|---|---|
| 有绑定有效的人裁 | 写人裁的字 | 不上（除非机器推翻人裁 → 复审格，文本仍是人裁字） |
| 机器放行、字变了，无人裁 | 按最新结果改（11-05 定：机器改字默认放行） | 不上 |
| **待审，首选字＝现行字** | 不动 | 上 |
| **待审，首选字≠现行字，现行有字** | **不动，等人裁定了再改**（11-10 定） | 上 |
| 待审，现行是 □（或缺格），有首选字 | 写首选字 | 上 |
| 待审，一个候选都没有 | 保持现行（多为 □） | 上 |
| 撤库重审格（字形库审阅撤库） | 不动（现行有字保持；□ 且无候选保持 □） | 上（复审格「撤库重审」） |
| 机器认定真阙文、现行有字 | 不动 | 上（复审） |
| 人裁定为阙文 | □＋`lacuna: true` | 不上 |

代码：manager `formats/guji_char_cord.apply_pending(current=)`、`swap/resolve.resolve`；cv `scripts/zhengli/republish.py`（`hold_pending_current`）。
要求 guji-manager ≥ v0.4.34、cv ≥ v0.6.35。

### 4. 三条铁律

1. **book-text 只放现状，不放问题和答案。** 待审原因、候选、票、人裁都不进 book-text；要知道「这格为什么还在审」去看待审单，要知道「人说过什么」去看事件。
2. **待审单可以随便换，book-text 少改。** 出一版新单不需要动 book-text；只有字真的定了（人裁、或机器放行改字、或 □ 有了首选字）才改 book-text。
3. **人裁只追加、靠锚绑定。** 不改旧事件；重切后靠锚重绑，绑不上就回待审单复审，绝不挂到别的字上。

## 四、常见问题

- **待审格在 book-text 里看不出来，读者会不会被误导？** 会显示首选字，可能是错的（例：殿本一处标题曾因参校本首选变成「雜史類臣三弁」）。这正是待审单要人看的格；网站上「待审」的标记读的是待审单，不是 book-text。
- **网站票算不算人裁？** 票在 KV 里只是意见；落成事件（`cellvotes` → `events`）之后才算，下一轮才进文本。
- **大模型裁定、点校放行算不算人裁？** 不算（`rulings`／`notes` 另存，不进人裁通道）。点校放行（两路同字 high、放行子集金标 0 错）写裁定库，下一轮由机器放行改字；它们改 book-text 走的是「机器放行」那一行。
- **重切后格号变了怎么办？** 待审单整张重出（按新格号）；人裁按锚重绑；book-text 按新切分重导出，按上表逐格判。
- **`decision.json`、char v0.4、`pending_reason` 写在 char 里？** 都已废弃（11-09）。

## 五、废弃说法对照

| 旧说法 | 现在 |
|---|---|
| 待审格在 book-text 里写 □、带 `pending_reason`（char v0.4 §4.8，11-03） | 写首选字或保持现字，不带任何标记（11-09） |
| `NNN.decision.json` 记看不出／切坏 | 删除；记录在待审单与人裁事件里（11-09） |
| 待审格首选字与现行不同按机器改字放行（11-09 初版） | 现行有字则不动，人裁后再改（11-10） |
| 未冻结册机器变字一律进待审复审（10-20） | 机器改字默认按最新结果进文本，只有推翻人裁才复审（11-05） |
